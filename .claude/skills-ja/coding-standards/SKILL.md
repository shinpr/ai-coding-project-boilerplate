# 普遍的コーディング規約

## 基本原則

ユーザー・運用者・保守者に必要な価値を届けつつ、システムの正しさと保守性を保てる、総合的な複雑性が最も低い解をエビデンスから選べる範囲まで調査する。

- **作業量より最終状態を優先** - 小さくするのは、変更後に残るもの（コード、テスト、概念、後の変更が知っておく必要のあること）の複雑さと量であり、そこへ至るまでの作業量ではない。プロダクトはこのセッションの後も変わり続け、残ったものは将来のエージェントが保守する。そのため、後に残るものが減るなら、より大きな変更でも今引き受ける。手順、編集、トークンが少なく済むことを理由に進め方を選ばない。作業量は、最終的な複雑さが同等の結果どうしで決める場合にだけ使う
- **現行要件に必要なコードだけを追加** - コードパス、機能、インフラ、抽象、起こるかどうか不明なエッジケースへの対処は、現行要件、検証済みの制約、根拠のある重大リスクが要求する場合に導入する（YAGNI）
- **根拠のある値** - 上限、タイムアウト、しきい値など振る舞いを決める値は、既存の要件、契約、計測、またはリポジトリ内で同じ目的に使われている値から取る。いずれからも決まらない場合は、仮定の値であることをコメントで示す
- **Design Convergence** - 現在必要な成果を、最終的なコードに残る設計要素が最小になる形で届ける。永続状態、公開コントラクトまたは境界を越える契約、振る舞いモード、再利用可能な抽象、コンポーネント分割を導入する前に、既存機能で何を満たせるか、現行の成果に何が不足しているか、その追加が不足を埋める最小の手段である理由を記録する
- **局所的な変更に耐える構造** - ここに次の変更を加えるのは、周辺のコードだけを読むエージェントである。そのため、変更が合わせなければならないものは、そのエージェントが見落とさない場所に置く。1か所の定義、型、網羅的な分岐、失敗するチェックのいずれかである。変更で追加・拡張するコードでは、正しい組み合わせだけを表せる形に状態を設計し、各状態は既存の所有者を通して進める。新しいコードでコンパイラ、型、lintのチェックが失敗した場合は、チェックが通るように構造を変える。抑制するのは、そうした構造の変更が存在しない場合だけとする

総合的な複雑性は、この設計で増えるユーザーの判断・設定・モード・概念・出力・永続状態・実装経路と、それらに伴うUX・実行時・テスト・文書・保守のコストで判断する。成立する案の間で実際に異なる観点だけを比較する。同じ必要な価値と証明をより低い複雑性で届けられる場合は、既存機能の再利用または新しい仕組みを追加しない案を選ぶ。

## コメント記述ルール

- **コードファースト**: 命名・型・構造を第一の表現手段とし、コードで表現できない情報を持つときだけコメントを書く。迷ったらコメントを足す前に命名を見直す
- **「なぜ」を説明し「何を」は書かない**: 判断の理由、トレードオフ、制約・エッジケース、公開APIの契約を説明する
- **現在も有効な内容**: コメントには現在の判断理由、制約、エッジケース、API契約を記載する。ドキュメントやその節を参照させると文書の更新でずれるため、内容はコメント自体に書く。開発履歴はバージョン管理に残す
- **タイムレス**: いつ読んでも有効な内容のみ記述
- **簡潔性**: 必要最小限の説明にとどめる

## エラーハンドリングの基本原則

### Fail-Fast原則
エラー時は速やかに失敗させ、不正な状態での処理継続を防ぐ。元の診断情報を保持したまま失敗を伝播するか、明示的な型付きエラーを返す。

詳細な実装方法（Result型、カスタムエラークラス、層別エラー処理など）は各言語・フレームワークのルールを参照。

## コード重複の判断基準

見かけの類似が偶然である間、または変更理由が異なる間は、具体的な実装を分けたままにする。同じビジネスルール、アルゴリズム、バリデーション契約、または一緒に変更すべき責務が複数の場所で保守されていることをリポジトリのエビデンスが示す場合に共通化する。

### 共通化の判断基準

**共通化すべきケース**
- ビジネスロジックの重複
- 複雑な処理アルゴリズム
- 一括変更が必要になる可能性が高い箇所
- バリデーションルール
- このリポジトリ内の複数の場所で一致させる必要がある事実: 名前、キー、パス、取りうる値が決まった集合、一方が書き込み他方が読み取るデータの形

**分離したままにするケース**
- 偶然の一致（たまたま同じコード）
- エビデンスが示す契約または変更理由の違い
- 共通化により可読性が著しく低下
- テストコード内の簡単なヘルパー

## 変更境界と参照の代表性

プロンプトで示されたパスは調査の起点である。別のリポジトリファイルが、受け入れ済みの成果を実装している、必要な依存または接続経路である、あるいは今回影響を受ける契約を保つために変更を要するとエビデンスが示す場合は、そのファイルも変更対象に含める。呼び出し元、利用側、テスト、設定、import、データフローは判断材料であり、必ずすべてを確認するチェックリストではない。

既存コードと変更の関係は2通りある。変更に依存するコードは、変更するコードへの参照から辿れる。同じ責務をすでに担うコードは、変更と名前も参照も共有していないことがある。位置と役割（同階層の機能、同じ層で同じ役割を持つファイル、共有層）と、受け取る入力と果たす目的から辿り、ロジックを比べて同じ責務かを判断する。実装や証明を変えうる候補を読んで判断した時点で止める。一致がない検索は、その検索で何も見つからなかったことしか示さない。

パターン、API、依存を採用する際は、対象機能と、同じ責務・現行契約を共有するリポジトリ内の利用箇所を調べる。その責務で互換性を保っている実装を優先する。使用頻度は候補の発見には役立つが、パターンの正当性を決めるものではない。複数の方式が共存する場合は、呼び出し元、ライフサイクル、互換性から、現行パターンとレガシーまたは無関係な方式を区別する。

外部依存のバージョンは、マニフェスト、ロックファイル、互換性のある利用側から確定する。それらの情報でも互換性またはアーキテクチャに関わる選択を確定できない場合にのみエスカレーションする。

## よくある失敗パターンと回避方法

### パターン1: 対症療法的な修正
**症状**: エラーや検出事項を1つ直すと新しいものが発生する、または同じ欠陥が別の経路から再発する
**原因**: 症状を現れた場所ごとに直し、それを生み出したものを残している
**回避方法**: 手元の失敗や検出事項を、それを生み出しているものまで辿る。同じ原因から生じた検出事項は、その原因で一度だけ直し、他の経路から再び生じないようにする

### パターン2: 型の保証の迂回
**症状**: どのチェックも契約も裏付けていない型を `any` や `as` で宣言している
**原因**: 型エラーを回避したい衝動
**回避方法**: 「型安全性の基礎」の根拠に関する基準を適用する。

### パターン3: テスト不足での実装
**症状**: 実装後にバグ多発
**原因**: 受け入れ済みの振る舞いを証明するテストがない
**回避方法**: 届ける各振る舞いを、それを観測できる境界で証明する

### パターン4: 未検証の前提に依存した実装
**症状**: 前提の誤りが判明した時点で、その前提に依存した作業が失敗する、または回避策が積み重なる
**原因**: 想定した機能、振る舞い、既存実装を事実として扱う
**回避方法**: 未検証の前提が、選んだアプローチを成り立たなくする可能性がある場合は、その前提に依存する作業を進める前に、十分な範囲で最もコストの低い手段で確認する。結果が前提と矛盾した場合は、部分ごとの修正を重ねる前にアプローチを見直す。この判断は今回のタスク内で行い、別の成果物は作らない。

### パターン5: 既存コード調査不足
**症状**: 重複実装、アーキテクチャ不整合、結合時の障害、古いパターンの採用
**原因**: 実装前の既存コード理解不足、近隣ファイルのみ参照し代表性を確認していない
**回避方法**:
- 実装前に、同じ責務をすでに担う機能と、変更に依存するコードを、上記「変更境界と参照の代表性」に沿って探す。類似機能が新しいコードと名前を共有しているとは限らない
- 類似機能を発見 → 現在の契約を満たす場合は、その実装を使用または拡張
- 変更が接続する、または類似する既存コードに問題がある（同じ事実が2か所に書かれている、表してはならない状態を表せる、新しいケースが迂回しなければならない形になっている など） → 改修することでこの変更の最終状態がより保守しやすくなる場合は、成果、要件、対象外を変えずに、この変更で改修する。問題を避けて組んだ変更は、問題と迂回の両方を残すためである。改修にアーキテクチャ判断が必要な場合はADRを作成する
- 類似機能が存在しない → 既存の設計思想に沿って新規実装
- 各判断とその根拠を、現在のワークフローがその記録先として割り当てた成果物に記載する

## デバッグ手法

### 5 Whys - 根本原因分析
各回答を観測済みの根拠に結び付け、修正によって元の失敗を防げる原因に到達するまで掘り下げる。各質問、根拠、最終的な因果関係を記録する。次の回答が推測になる時点で止め、必要な根拠を明記する。

## 型安全性の基礎

**型安全の原則**: 型の絞り込みには、実行時の検査または既存の契約を根拠とする。型ガードが保証する型は、実際の検査内容に一致させる。

- 構造が確定していない入力には `unknown` を用い、利用側が必要とするプロパティを検証する。
- 型の関係やバリエーションは、ジェネリクス、ユニオン型、インターセクション型で表現する。
- 取りうる値が決まった同じ集合で複数の場所が分岐する場合は、その集合をリテラルのユニオン型にし、各メンバーを明示的に扱って最後に `never` チェックを置く。これにより、メンバーを追加するとすべての分岐で型チェックが失敗する。
- 検証済みのSDK・フレームワーク契約に基づくアサーションは、該当する境界に置く。静的解析でその契約を表現できない場合は、抑制を対象ルールに限定し、契約の根拠とアサーションの適用範囲を記載する。

**型の複雑性のレビューシグナル**

合否のしきい値ではなく、見直しのきっかけとして使う。既存のプロジェクト規約とその型の責務を優先する。

- フィールド数が20を超える: 型が複数の責務を混在させていないか見直す
- オプショナル率が30%を超える: 必須と任意の形を分けるべきか見直す
- ネストが3階層を超える: フラット化を見直す
- **外部API型の扱い**: 外部の実際の形を表現し、アプリケーションの境界で変換する

## 実装作業の完全性担保

### 影響範囲の追跡

実装の前に、変更するコードの呼び出し元、依存関係、データフロー（生成→変更→参照）を、「変更境界と参照の代表性」で定める変更境界を変えうるファイルを確認し終えるまで追跡する。実装やその検証が依拠する直接・間接の影響は、その作業に引き継ぐ。

### 未使用コード削除ルール

今回の変更によってコード、ドキュメント、設定が不要になった場合:
- 呼び出し元と、生成・運用上の利用を確認したうえで、同じ変更で削除する。以前の実装はバージョン管理に残る
- 不要かどうかが不確かな場合、または削除が受け入れた成果の範囲を超える場合は、残して報告する
- 関係のない休眠コードは実装スコープの外に置く

## テスト設計原則

### テストケースの構造
- テストは「準備（Arrange）」「実行（Act）」「検証（Assert）」の3段階で構成
- テスト名でトリガーと観測可能な結果を示す
- 1つのテストケースでは1つの振る舞いのみを検証

### テストデータ管理
- テストデータは専用ディレクトリで管理
- 環境変数はテスト用の値を定義
- 認証情報、トークン、個人データ、決済情報には、合成した非機密値を使用
- テストデータは最小限に保ち、テストケースの検証目的に直接関連するデータのみ使用

### モックとスタブの使用方針

**推奨: 単体テストでの外部依存モック化**
- メリット: テストの独立性と再現性を確保
- 実践: DB、API、ファイルシステム等の外部依存をモック化

**Unit testの境界**: 外部接続には決定論的な代替を使用する。実際の外部境界は、その契約を対象として選定したIntegration testまたはE2E testで検証する

### テスト失敗時の対応判断基準

**テストを修正**: 間違った期待値、存在しない機能参照、実装詳細への依存、テストのためだけの実装
**実装を修正**: 妥当な仕様、ビジネスロジック、重要なエッジケース
**どちらの解釈も参照できる要件と両立する場合**: 未解決の振る舞い判断として差し戻す — 2つの候補となる振る舞い、どちらが正しいかを決める出所、および一方を選ばず停止する条件を示す

## テストの粒度原則

### 原則：観測可能な振る舞いのみ
**観測可能な境界を通じてテストする**：公開API、戻り値、例外、外部呼び出し、永続化された状態を検証する。privateメソッド、内部状態、アルゴリズムの詳細は、これらの観測可能な境界を通じてのみ到達する。

## Security Principles

### Secure Defaults
- 認証情報とシークレットは環境変数または専用のシークレットマネージャーで管理
- すべてのデータベースアクセスにパラメータ化クエリ（プリペアドステートメント）を使用
- 言語またはフレームワークが提供する確立された暗号ライブラリを使用
- セキュリティ上重要な値（トークン、ID、nonce）は暗号学的に安全な乱数生成器で生成
- 機密データは標準プロトコルを使用して保存時・転送時に暗号化

### Input and Output Boundaries
- システムのエントリポイントで、期待される形式・型・長さについてすべての外部入力を検証
- 出力をレンダリングコンテキスト（HTML、SQL、シェル、URL）に応じて適切にエンコード
- エラーレスポンスには呼び出し元に必要な情報のみを返却し、詳細な診断情報はサーバーサイドでログに記録

### Access Control
- ユーザーデータを扱うまたは状態変更をトリガーするすべてのエントリポイントに認証を適用
- エントリポイントだけでなく、各リソースアクセスで認可を検証
- 操作に必要な権限のみを付与（ファイル、データベース接続、APIスコープ）

### Knowledge Cutoff Supplement (2026-03)
- OWASP Top 10:2025は症状から根本原因へと視点を移し、「Software Supply Chain Failures」(A03)と「Mishandling of Exceptional Conditions」(A10)が追加された
- 最近の研究ではAI生成コードがAccess Controlの欠落を高い発生率で示しているため、認証と認可を高優先度のレビュー対象として扱う
- OpenSSFが「Security-Focused Guide for AI Code Assistant Instructions」を公開した。汎用的なアドバイスより、言語固有で実行可能な制約を推奨している
- 詳細な検出パターンは`references/security-checks.md`を参照

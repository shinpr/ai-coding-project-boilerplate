# レビュー裁定（Review Resolution）

成果物のレビュアーまたは検証エージェントが、修正・進行・エスカレーションを振り分けうる検出事項を返した場合に、このプロトコルを使用する。下流の専門エージェントがエビデンスとして消費する検証出力は、その専門エージェントへのハンドオフの一部として扱う。

オーケストレーターはレビュー結果をエビデンスとして扱い、出典ドキュメントからワークフローの判断を下す。

## 1. 全ての検出事項を評価する

処理方針を割り当てる前に、現在の成果物の該当箇所、引用されたリポジトリ上のエビデンス、出典ドキュメントを確認する。レビュアーの主張は、検証すべきエビデンスとして扱う。

オーケストレーターは、対応可能な各検出事項に対して処理方針を1つ記録する:

| 処理方針 | 使用条件 |
|---|---|
| `apply` | 現在の成果物を変更しないままだと、確定した成果を妨げる、拘束力のある要件・設計判断・リポジトリのルールに違反する、または必要な正しさや検証が裏づけられないまま残る。 |
| `decline` | 現在の成果物を変更しないままでも確定した成果を達成し、拘束的な制約と必要な正しさ・検証を満たす。検出事項が提案しているのは、スコープの追加、除外の取り消し、任意の堅牢化や一般的な整理、証明の重複、レビュアーが宣言した成果物境界の外にある性質への依存、またはその境界の外にある別作業である。 |
| `user_decision_required` | 検出事項の解決が、確定したプロダクト成果・除外事項・承認済みの主要な設計判断を変える、またはユーザーのみが持つ権限を必要とする。 |

確認済みのセキュリティリスクと出典ドキュメントとの矛盾は `apply` または `user_decision_required` とする。コストの高さだけではこの分類は変わらない。

各検出事項について記録する内容:

- 安定した検出事項ID
- 処理方針
- 出典上の根拠と具体的なエビデンス
- `decline` の場合はその理由

処理方針がルーティングを決める。`apply` では、レビュアーが返した検出事項オブジェクトを全フィールド・全値そのままの形で転送し、`apply` の処理方針だけを付加する。この逐語転送がレビュアーの文脈を保つ。オーケストレーターは検出事項のいかなる部分も、要約・抜粋・言い換え・再解釈・補足・置換しない。修正内容は、出典ドキュメントに基づいて author または executor が決める。出典から決められず、ユーザーのみが持つ権限を要する修正になる場合は `user_decision_required` を割り当て、セクション3へ進む。

対応不要のレビュアー提案は、最終のユーザー向け報告に残す。author または executor へのハンドオフに入るのは、`apply` の検出事項と、セクション3で `maintained` となった `apply` の検出事項のみである。

## 2. 修正と再検討

`apply` の検出事項オブジェクトを、処理方針とともに逐語で author または executor に渡す。レビュアーへの再レビューでは、初回レビュー時の入力をそのまま再利用し、`prior_feedback` を `{ id, disposition, reason?, evidence }` の配列として追加する。

修正の評価範囲は、受領した項目ちょうどそれだけである。レビュアーはその範囲を完了した上で、次を行う:

- `apply` を適用した項目は、変更した境界に修正起因のリグレッションがなく成果物が検出事項を満たすことを現在のエビデンスが示す場合にのみ `resolved` とする。それ以外は現在のエビデンスを添えて `maintained` とする
- `decline` とした検出事項は、現在のエビデンスと出典ドキュメントがもはやそれを支持しない場合に `withdrawn` とする。それ以外は現在のエビデンスを添えて `maintained` とする
- 受領した各IDについて、`prior_feedback_reconciliation` エントリをちょうど1つ出力する

修正再レビューのステータスまたは判定は、これらの照合エントリのみから導出する。修正ループがカバーするのは受領した項目だけであり、受領IDのいずれにも該当しない、修正が新たに持ち込んだ欠陥は、このループを広げるのではなく品質ゲートと実装後の検証サイクルで検出する。レビュアー自身の安全側 `blocked` トリガー — 不可逆リスクまたはコミット済みシークレットの境界 — に該当する状態を新たに観測した場合は、適用した修正がその原因かどうかに関わらず、ただちにそのステータスで返す。独立した事実検証エージェントが同じ差異を再度指摘することはある。その処理方針はオーケストレーターが出典上のエビデンスから割り当てる。

## 3. 収束またはエスカレーション

修正再レビューのエントリを、記録された `prior_disposition` に従って処理する:

- `resolved` と `withdrawn` は完了
- `prior_disposition: apply` の `maintained` は、元の検出事項と照合エントリ全体を逐語で同じ author / executor の経路に戻し、その後もう一度修正再レビューを行う
- `prior_disposition: decline` の `maintained` は、その decline を維持し、修正サイクルを再開しない

エスカレーションする条件: 同一IDの `prior_disposition: apply` が2回連続で `maintained` を返した、処理方針が `user_decision_required` である、ユーザーのみが持つ権限が必要である、不可逆な操作が承認待ちである、または必要な入力が実際に使用不能である。進行してよいのは、`prior_disposition: apply` の `maintained` エントリが残っておらず、対応可能な他の全検出事項に処理方針があり、各 `user_decision_required` 項目にユーザーの判断が記録された後である。

この検出事項単位のループは、親スキル「実装後検証の合否基準」にある検証エージェント単位のサイクル上限とは別物である。あちらは実装後の検証エージェント群を何回まで再実行するかを制限し、こちらは1つの検出事項IDが何回まで `maintained` を返せるかを制限する。両方が適用され、先に到達した方でエスカレーションする。

ハンドオフに含めるのは、次のちょうどこの集合である:

- 元のレビュー対象の識別子
- 再レビュー時は、初回レビューの入力をそのまま
- `apply` の検出事項オブジェクト全体を逐語で、オーケストレーターの処理方針のみ付加したもの
- `maintained` の `apply` 検出事項を author / executor に戻す場合は、照合エントリ全体
- 次の消費側がレビュアーの照合結果を受け付ける場合は、`decline` としたIDとその理由・エビデンスを `prior_feedback` として

author へのハンドオフには、これ以外にオーケストレーターが書いた意味内容を含めない。

最終のユーザー向け報告には、`decline` とした対応可能な各検出事項を、そのID・出典上の理由・エビデンスとともに列挙する。

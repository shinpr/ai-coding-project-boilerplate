# E2Eテスト設計（ブラウザハーネス）

このリファレンスでは、本ワークフローが標準E2Eブラウザハーネスとして想定するPlaywrightを全編のデフォルト例に用いる。プロジェクトが別のフレームワーク（Cypress、Selenium等）を選択している場合はパターンを適応させる。証明境界のルールは変わらない。

## 2つのE2Eレーン

本ワークフローのE2Eテストは2つのレーンに分かれる（親スキルの「テスト種別と選定」を参照）:

| レーン | 適用条件 | 証明境界 | コスト |
|------|---------|---------|-------|
| **fixture-e2e** | 決定論的フィクスチャ（モックバックエンド/フィクスチャデータ）を用いたUIジャーニー検証 | 実ブラウザが主張の境界であり、バックエンドの振る舞いはフィクスチャ状態として与える | フィクスチャのセットアップを用いてCIで実行できる |
| **service-integration-e2e** | ジャーニーの正しさが実サービス間の振る舞い（データ永続化、トランザクション整合性、外部契約）に依存する | 起動済みサービスの境界自体が主張の一部である | セットアップと保守のコストが高い。その境界だけが故障を露呈できる場合に選択する |

両レーンとも通常はPlaywrightを使用する。違いは、バックエンドがモック/フィクスチャ駆動か、実際に動作しているかである。

## E2Eテストを作成する場合

E2E候補は、複数ページにまたがるか、実ブラウザ操作を必要とする**クリティカルなユーザージャーニー**を対象とする。検証に実サービスが必要かどうかでレーンを選択する。

### 候補の性質

E2E候補とは、出典となる成果物に記録された、次のいずれかの性質を持つ振る舞いである:

| 性質 | E2E候補となる理由 |
|------|-----------------|
| 複数画面にまたがる | 約束された成果が、画面遷移の連なりを経て初めて観測可能になる |
| 実ブラウザを要する | ナビゲーション、Cookie、ストレージ、実DOM描画が結果を左右する |
| 遷移しないと到達できない状態 | in-processでは再現できないエラー、empty、loading状態である |
| ブラウザ依存のインタラクション | ドラッグ&ドロップ、キーボードナビゲーション、レスポンシブ動作である |

出典となる成果物を読み、これらの性質に対応付けるのはエージェントの役割である。本スキルは成果物のセクション名を指定しない。

### 選定基準

**対象**:
- 複数ページにまたがるユーザージャーニー（ログイン → ダッシュボード → 操作 → 確認）
- 実ブラウザAPIを必要とするフロー（ナビゲーション、Cookie、localStorage）
- 実DOM描画が必要なアクセシビリティ検証
- viewportをまたぐレスポンシブ動作

**代わりに統合テストを使用する場合**:
- 単一コンポーネントの状態変化 → in-processのコンポーネントレンダラ（React/TSではRTL）
- APIレスポンス処理 → in-processのAPIモック + コンポーネントレンダラ（React/TSではMSW + RTL）
- 純粋なデータ変換 → ユニットテスト

## 候補の記録

選択した各候補を次の形で記録し、下流の実装が証明に関する判断を維持できるようにする。

### マッピングテンプレート

```
画面遷移: [画面A] → [画面B] → [画面C]
AC参照: AC-{id}
ユーザージャーニー: [ユーザーが達成する内容の説明]
レーン: fixture-e2e | service-integration-e2e
前提条件: [認証状態、データ状態 — フィクスチャ駆動かライブかを明記]
検証ポイント:
  - [各ステップでアサートすべき内容]
主要な故障: [テストを失敗させるべきリグレッション]
証明義務: [テストが実行すべき境界と観測可能な状態]
```

**レーン判定**: デフォルトは`fixture-e2e`を選択する。検証に実サービス間の振る舞いの観測が必要な場合（例: 実DBへの書き込みをまたいでデータが永続化すること、外部サービスが正しいペイロードを受信することをアサートする場合）は、`service-integration-e2e`へ移す。

## Playwrightテストアーキテクチャ

### ページオブジェクトパターン

保守性のために、ブラウザ操作をページオブジェクトで整理する:

```
tests/
├── e2e/
│   ├── pages/                       # ページオブジェクト（レーン間で共通）
│   ├── fixtures/                    # テストフィクスチャとヘルパー（auth、seed）
│   ├── data/                        # fixture-e2e用の静的フィクスチャデータ
│   ├── *.fixture-e2e.test.ts        # fixture-e2eテストファイル
│   └── *.service-e2e.test.ts        # service-integration-e2eテストファイル
```

### テストの分離

- 各テストはクリーンなブラウザコンテキストから開始する
- テスト間で状態を共有しない
- 共通セットアップ（認証、ナビゲーション）には`beforeEach`を使用する
- セットアップではテスト内ナビゲーションより`page.goto()`を優先する

### Viewportテスト

UI Specでレスポンシブ動作が定義されている場合、重要なbreakpointをテストする:

| Breakpoint | 幅 | テスト条件 |
|-----------|----|-----------|
| モバイル | UI Specのbreakpointまたは設定済みのmobile project viewport | UI Specでモバイル固有のインタラクションが定義されている場合 |
| タブレット | UI Specのbreakpointまたは設定済みのtablet project viewport | UI Specでタブレット用レイアウトの差異が定義されている場合 |
| デフォルト | Playwright project viewportまたはUI Specのbaseline | 選択した各レスポンシブジャーニー |

## 最小セットの確認

- 出力する各E2Eテストは、より安価なテストではまだ証明されていない受理済みの証明義務をカバーする。
- 出力しない各E2E候補は、別の場所でカバーされている、別シナリオと重複する、またはブラウザ/システム境界を必要としない。
- 1つのまとまったジャーニーで複数の義務を証明でき、各アサーションと故障の対応を追跡できる場合は、そのジャーニーを優先する。
- 個別の実害ある故障からテスト数を決め、そのすべてをカバーする最小のセットを残す。

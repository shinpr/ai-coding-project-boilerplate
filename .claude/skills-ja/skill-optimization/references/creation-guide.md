# スキル生成ガイド

ユーザーの生の知識から新規スキルコンテンツを生成するためのガイド。

## 生成フロー

構造、表現、コンテキスト、制約、例を変える前に、与えられた知識と要件を原文のまま保持する。以下の3つのゲートを通じて、Phaseの状態は1つだけを維持する。

### Step 1: 分析

**入力**: ユーザーの生の知識（ルール、パターン、具体例、判断基準）

**手順**:
1. コンテンツを分類: 定義、パターン、プロセス、基準、具体例
2. BPパターン（BP-001〜BP-009）で問題を検出
3. サイズ見積もり: small（80行未満）、medium（80-250行）、large（250行以上）
4. スキルがorchestrationまたはselectionを担うかを特定する。該当する場合は必要なskill referenceを記録する。pure execution skillでは、実行に不可欠でlocalに持つべきcontextを特定する

**出力証跡**:
- 元の要件と意図した成果
- BP-001〜BP-009の網羅結果
- 一意な指摘ID、重大度、場所、引用した根拠を含む問題一覧
- 保持すべき要件と未解決の入力

**分析ゲート**: すべてのBP patternを確認し、各問題に根拠があり、保持すべき要件が明示され、忠実な生成を妨げる未解決の入力がない場合にのみ次へ進む。

### Step 2: 最適化済みコンテンツの生成

**入力**: 分類済みコンテンツ + 検出リスト

**手順**:
1. 優先度順に変換を適用: P1 → P2 → P3
2. 標準セクション順序で構造化:
   - コンテキスト/前提条件
   - 中核概念（定義、パターン）
   - プロセス/手順（ステップ形式）
   - 出力形式/具体例
   - 品質チェックリスト
   - 参照
3. **バランス確認**:
   - 過剰最適化: ユーザー入力の範囲を超えている → 削減
   - 可読性低下: 構造化で要点が不明瞭 → 簡素化
4. 10原則の合否を確認

**出力証跡**:
- 指摘ごとに1つの適用または見送りの解決方法
- すべての変更から指摘または明記されたプロジェクト情報源への対応
- 保持すべき要件をすべて含む`SKILL.md`候補

**最適化ゲート**: 各指摘が1回だけ解決され、候補が自己完結し、元の意図を保持している場合にのみ次へ進む。

### Step 3: バランス確認

意図の保持、判断に必要な情報、情報密度、制約の必要性、作業量の妥当性、追跡可能性を評価する。明記された指摘を解消する、または保持すべき要件を守る調整だけを適用する。

**出力**: 完成した`SKILL.md`と、実行フローに必要な同一ディレクトリ内のreferenceまたはscriptの内容。

**バランスゲート**: 適用対象の確認項目がすべて成功した場合にのみ確定する。不明点によって確認できない場合は作業を止め、必要な根拠またはユーザー判断を具体的に示す。

## description記述の指針

スキルのfrontmatter `description`フィールド向け:

**基本原則**: descriptionはエージェントの**トリガーメカニズム**であり、人間向けの要約ではない。エージェントはベースライン能力を超える知識が必要なタスクにのみスキルを参照する。descriptionは、このスキルがエージェントにない価値を提供する理由を伝える必要がある。

| ルール | 例 |
|--------|-----|
| 三人称・動詞始まり | 「コード品質を検査。」（「このスキルは〜」としない） |
| 使用場面を含める | 「機能実装、コードレビュー時に使用。」 |
| 200文字前後を目安 | 短いほど全スキル読み込み時のコンテキスト圧迫が減る |
| 具体的に記述 | 「9つのコンテンツパターンを適用」（「品質を改善」としない） |
| 実装詳細を含めない | 何をするかを記述し、どうやるかは記述しない |

**テンプレート**: `{対象}を{プロジェクト固有の基準/パターン}で{動詞}。{ユーザーがこの作業を依頼する際のフレーズ}時に使用。`

**description品質チェックリスト**:
- [ ] プロジェクト固有の用語・クラス名・パターンを含む（一般LLM知識と差別化）
- [ ] ユーザーが実際に使うフレーズを含む（「テスト追加して」「エラーハンドリング見て」等）
- [ ] ユーザーの意図にフォーカスしている（スキル内部構造の説明ではなく）
- [ ] 一般知識のみで構成されたスキルは不要の可能性がある — プロジェクト固有の内容が含まれているか確認
- [ ] pure skillは単独で読み込んでも実行でき、独立して読み込まれるsibling skillを前提条件としない

## 圧縮と分割

分割前に次を行う:

1. ベースライン知識、重複、観測済みの反復障害または必要な境界に結び付かない是正規則を削除する。
2. 網羅的な分岐を、目的、根拠、選択基準に置き換える。
3. 非自明な対応関係や例外を示さない例を削除する。
4. 毎回同じ処理になる決定論的な操作をスクリプトへ移す。
5. 読み込み条件と判断への影響が明示された条件付き詳細だけを残す。

圧縮後も400行を超える場合は、残った条件付き詳細を1階層下の`references/`へ分割する。250行の目標を超える本文は、該当セクションを削除するとベースライン外の判断、必要な境界、利用側の契約、または観測済みの反復障害への対応が変わる場合に限り許容する。実行に必要な規則は`SKILL.md`に保持するか、同一ディレクトリのreferenceを読み込む明示的なゲートを設ける。各pure skillはsibling pure skillの読み込みなしで実行可能にする。

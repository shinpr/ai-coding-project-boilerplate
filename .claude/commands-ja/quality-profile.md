プロファイルの条件を提案または記録する前に、Skill: llm-friendly-contextを実行する。
一般的なコード品質の知識と、リポジトリ固有の基準を区別するために、Skill: coding-standardsを実行する。

## 目的

コードレビューで使うリポジトリ固有の合格条件をユーザーと確定し、`docs/project-context/quality.yaml`を作成または更新する。

依頼された基準の変更: $ARGUMENTS

## プロファイル契約

```yaml
version: 1
review_dimensions:
  - id: stable-kebab-case-id
    applies_when: このリポジトリの基準が変更に適用されることを示す観測可能な条件
    pass: 検証すべき、観測可能な合格状態
    evidence:
      - "repository/path: セクション、識別子、または契約"
```

各観点は、リポジトリ固有のレビュー判断を1つだけ扱う。`applies_when`はレビュー対象を限定し、`pass`は合格状態を定め、`evidence`はその基準がこのリポジトリに属する根拠を示す。

## 作成手順

1. 現在の作業リポジトリを対象とし、`docs/project-context/quality.yaml`が存在する場合は読み込む。既存のプロファイルを更新する場合は、依頼された基準の変更だけを更新範囲とする。変更内容が指定されていなければ確認し、プロファイルは変更しない。
2. リポジトリの指示、コントリビューター向けドキュメント、CI、マニフェストとスクリプト、スキーマと公開契約、テスト、代表的な実装パターンで明示または強制されている合格条件から候補を作る。更新時は、依頼された変更だけから候補を導き、関係のない観点を維持する。
3. 各候補について、適用条件、合格状態、リポジトリ固有の基準であるかという判断を変えうる範囲で、支持するエビデンスと否定するエビデンスを調べる。観測済みのリポジトリの事実と、ユーザーの確認が必要な基準上の選択を分ける。
4. `pass`条件を満たさないことが実装の合否を変え、依存するリポジトリの事実がすべてエビデンスで示される候補だけを残す。`applies_when`は有用な最小範囲に絞り、`pass`には観測可能な肯定形の条件を1つ記載する。同じ検出事項と修正になる候補はまとめる。必要なリポジトリのエビデンスが得られない候補は省き、必要なエビデンスを具体的に報告する。
5. 追加、変更、削除の案を提示し、それ以外の観点を変更しないこと、支持するエビデンスと否定するエビデンス、未解決の基準上の選択とレビュー結果への影響を示す。未解決の選択がない案について、記録前にユーザーの明示的な確認を得る。
6. 確認された内容だけを記録する。結果を読み直し、versionが`1`であること、IDが重複していないこと、必須フィールドが揃っていること、条件が観測可能であること、エビデンスの参照先を読めること、確認済みの案と一致することを検証する。

リポジトリ固有の観点が1つも残らず、プロファイルも存在しない場合は、リポジトリのエビデンスから記録すべき内容がないことを報告し、リポジトリを変更しない。

## 結果

確認前に次を報告する。

- 追加、変更、削除の案と、変更しない残りの内容
- 各変更を支持するエビデンスと否定するエビデンス
- 省いた候補と、不足しているエビデンス
- ユーザーの判断が必要な基準上の選択と、レビュー結果への影響

確認後に次を報告する。

- プロファイルのパスと、作成、更新、変更なしのいずれであるか
- 追加、変更、削除した観点
- 変更した各観点に使ったエビデンス
- 結果を検証できなかった場合は、証明不足を具体的に示す

## 完了チェック

- [ ] 条件が肯定形かつ観測可能で、`applies_when`によって適用範囲が限定されている
- [ ] プロファイルにはリポジトリ固有の合格条件だけが含まれている
- [ ] 提案を変えうる場合に、支持するエビデンスと否定するエビデンスを比較した
- [ ] リポジトリへ書き込む前に、案全体についてユーザーの確認を得た
- [ ] 更新範囲外の観点を変更していない
- [ ] 記録したプロファイルがプロファイル契約を満たしている

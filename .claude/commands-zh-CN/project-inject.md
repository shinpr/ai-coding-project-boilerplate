---
description: 通过模板驱动的访谈配置 project-context 技能
---

在编写 Agent 提示词、交接内容或生成的产物之前，执行 `llm-friendly-context` 技能（使用 Skill 工具）。

**命令上下文**：`/project-inject` 收集能提升 AI 执行准确度的项目专属前提信息，并将其写入 `project-context` 技能。访谈是模板驱动的：章节目录存放于 `references/template.md`，需要新增维度时编辑该模板即可。

## 为什么需要它

CLAUDE.md 的会话初始化会在每次会话开始时加载 `project-context/SKILL.md`。此处收集的信息直接影响 AI 在所有任务中的判断准确度。已配置的 SKILL.md 要保持精简——每一行都会消耗每次会话的上下文预算。

## 执行流程

按顺序完成第 1-6 步。仅当当前步骤规定的检查点或用户决策得到满足时，才推进到下一步。在验证步骤成功之后再呈现结果。

### 第 1 步：加载输入

1. 阅读 `.claude/skills/project-context/SKILL.md`，了解当前状态。根据正文中出现的目录章节标题（`## 项目概述`、`## 领域约束`、`## 质量标准`、`## 开发阶段`、`## 目录约定`、`## 外部资源`）的数量来区分两种情况：
   - **未配置** —— 正文中的目录章节标题为 0 个。
   - **已配置** —— 正文中的目录章节标题为 1 个或以上。
2. 阅读 `.claude/skills/project-context/references/template.md`，获取章节目录。

**检查点**：你已掌握 `template.md` 中的章节目录，以及 `SKILL.md` 处于已配置还是未配置的状态。

### 第 2 步：构建章节计划

针对目录中的每个章节，产出逐章节的计划（`add` / `keep` / `update` / `remove` / `skip`）。

**未配置的情况**：
- 项目概述：`add`（必需；该章节的纳入规则为“始终纳入”）。
- 对其余每个目录章节使用 AskUserQuestion 提问：“要添加 `<章节名>` 章节吗？” 选项：“是，添加” / “否，跳过”。据此标记 `add` 或 `skip`。

**已配置的情况**：
- 对当前已填写内容的每个章节使用 AskUserQuestion 提问：“对现有的 `<章节名>` 章节采取什么操作？” 选项：“保持原样”（标记 `keep`）/ “更新 —— 替换现有内容”（标记 `update`）/ “移除 —— 从重建的 SKILL.md 中删去”（标记 `remove`）。
- 对现有 SKILL.md 中仍为空的每个目录章节使用 AskUserQuestion 提问：“要添加 `<章节名>` 章节吗？” 选项：“是，添加”（标记 `add`）/ “否，跳过”（标记 `skip`）。

**检查点**：每个目录章节都恰好有一个处置结果：`add`、`keep`、`update`、`remove` 或 `skip`。

### 第 3 步：逐章节执行访谈

对每个标记为 `add` 或 `update` 的章节，执行 `template.md` 为该章节定义的询问协议。该目录规定了 AskUserQuestion 的提问文本与选项、纳入规则，以及每个章节的输出结构。

**外部资源章节**：遵循 `template.md` § 外部资源 中的路由协议。该章节负责领域多选、领域到文件 slug 的映射，以及各维度的输出 schema；本命令委派给它。

**模糊表述拒绝规则**（适用于每个 `add` 和 `update` 章节）：当用户提供的规则使用主观表述时（例如“注意性能”），追问：“AI 要如何验证这条规则是通过还是不通过？请将其改写为可度量的检查项，或回复 `drop` 以省略。”以可度量形式给出的规则原样采用；主观的规则替换为用户改写后的版本，用户回复 `drop` 时则省略该规则。

**检查点**：你已掌握每个 `add` 和 `update` 章节采集到的内容，以及每个 `keep` 章节逐字保留的原始内容。

### 第 4 步：组装并写入 SKILL.md

按以下顺序拼接，构建重建后的 SKILL.md：

1. Frontmatter —— 原样写入以下标准块：
   ```
   ---
   name: project-context
   description: 提供 AI 执行准确度所需的项目专属前提信息 —— 领域约束、仓库专属的质量标准、开发阶段、目录约定、外部资源的访问方法。在会话开始时、确认项目结构时，或任务引用领域规则、仓库专属的质量标准、仓库之外的外部资源时使用。
   ---
   ```
2. `# 项目上下文` 标题。
3. 按目录顺序排列各个章节（项目概述 → 领域约束 → 质量标准 → 开发阶段 → 目录约定 → 外部资源）。输出仅包含处置结果为 `add`、`keep` 或 `update`，且满足其纳入规则的章节；正文从一个已纳入的章节直接推进到下一个。

将组装好的内容写入 `.claude/skills/project-context/SKILL.md`。这是 Claude 在每次会话中读取的唯一运行时依据。

### 第 5 步：验证

对重建后的 `.claude/skills/project-context/SKILL.md` 依次应用下列每一项检查：

- [ ] Frontmatter 与第 4 步中的标准块逐字一致。
- [ ] 正文中每个章节标题之后，都紧跟访谈采集到的具体内容（具体取值、列表或子块）。
- [ ] 每个已填写内容的章节，都符合 `template.md` 为其定义的输出结构。
- [ ] 正文中的每个章节，处置结果均为 `add`、`keep` 或 `update`，且满足其纳入规则。
- [ ] 领域约束的陈述可按通过/不通过判定（例如“日志条目使用匿名化 ID”通过；“日志保持干净”则通不过此项检查）。
- [ ] 每条质量标准都具备可观测的适用条件、一个可观测的肯定形合格状态，以及支撑的证据。
- [ ] 项目上下文的内容仅限于仓库专属的约束、质量标准、阶段、规范和外部资源。技术栈细节属于 `technical-spec` 技能；通用实现原则属于 `coding-standards` 技能。

任一检查未通过时，向用户报告未通过的检查项并指出具体行，同时提议对受影响的章节重新访谈或进行手动编辑。修复后重新执行第 5 步。

### 第 6 步：呈现结果

向用户展示重建后的 SKILL.md，列出所做的变更（新增 / 更新 / 移除 / 保留的章节），并确认完成。

## 输出示例

**对未配置的技能首次运行**（所有章节均为全新采集）：

```
project-context 配置完成:
- 保留的章节: （无 —— 首次运行）
- 更新的章节: （无 —— 首次运行）
- 新增的章节: 项目概述、领域约束（采集到 2 条规则）、质量标准（采集到 2 条标准）、开发阶段、目录约定（1 条规则）、外部资源（后端领域 —— 数据库 schema 来源、密钥存储）
- 移除的章节: （无）
- 写入的文件：.claude/skills/project-context/SKILL.md
```

**对已配置的技能做轻量更新**（编辑一个章节，其余保留）：

```
project-context 更新完成:
- 保留的章节: 项目概述、开发阶段、目录约定
- 更新的章节: 领域约束（采集到 3 条规则）
- 新增的章节: （无）
- 移除的章节: （无）
- 写入的文件：.claude/skills/project-context/SKILL.md
```

**仅做精简的运行**（移除一个现有章节，不新增）：

```
project-context 更新完成:
- 保留的章节: 项目概述、领域约束、开发阶段
- 更新的章节: （无）
- 新增的章节: （无）
- 移除的章节: 目录约定
- 写入的文件：.claude/skills/project-context/SKILL.md
```

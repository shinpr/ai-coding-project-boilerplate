# 收敛判定标准

四个收敛字段的判定规则。在引出或评估它们时阅读本文。

## outcome（预期结果）

该变更必须产生的一个可观测结果，而不是一份功能清单。

无法追溯到该 outcome 的需求属于多余项：应删除，或让用户扩大 outcome 以覆盖它。

## requirements[] — 层次划分

| 层次 | 含义 | 现在可构建 |
|-------|---------|---------------|
| `current-state` | 已存在的行为 | 否——这些是事实，不是工作项 |
| `desired-future` | 用户所要求的变更 | 是 |

评估性请求、设想性想法和指定的实现机制，作为候选项保留在当前请求上下文中。`requirements[]` 以及需长期保留的需求/设计文档，只接收用户明确提升为 `desired-future` 的候选项；一份已接受的 ADR 可以将已评估的选项保留为决策历史。

将当前状态、期望的未来状态和候选项混在同一份需求清单里，会让一份臃肿的计划看起来是连贯的，因为其中每一项读起来都同等地“必需”。为每个与构建相关的项目打上标签；当某项的 current-state 或 desired-future 角色不明确时应向用户询问，而不是自行推断。

## nonGoals[]（非目标）

由用户明确表述的、本次变更有意排除的能力。

先呈现成本分级及其未知项——若成本未分级，则呈现分析得出的范围事实——然后询问需要排除什么。`userAgreedNone` 记录的是用户已考虑过排除项但未发现需要排除的内容；只能由用户设置该字段。

智能体自行注意到的相邻能力，应作为向用户提出的问题，而不是直接定为非目标。

## cost（成本）

成本取决于结构和数量，而非行为，因此仅依据以下输入来判定：

| 输入 | 获取方式 |
|-------|--------------------|
| 需变更的目标数量与种类 | 对受影响文件执行 Grep/Glob |
| 跨越的边界数量 | 受影响路径的构成，加上 import 与调用方追踪 |
| 是否已存在等效实现（复用还是新建） | 对相似名称或结构执行 Grep |
| 是否需要转换持久化状态 | 变更集中是否包含 schema 或迁移路径 |
| 是否已有验证支持 | 对该领域现有测试工具执行 Glob |
| 尚存在哪些未知项 | 通过 WebSearch 查询某依赖当前的能力；以及以上方式无法解决的其他事项 |

阅读代码*实际做了什么*，回答的是变更是否正确，而不是变更的成本，这属于设计之前的代码库分析范畴。

将 `cost` 记录为一个分级、上述用于判定该分级的输入，以及尚存的未知项。只有在明确声明超出范围时才可跳过 `cost`；若无此声明，则必须对其分级。

## 挑战力度

分级的唯一作用是从下表中选定一行，这样成本低的需求就能保持低成本地被接受。

| 分级 | 含义 | 挑战方式 |
|------|---------|-----------|
| `low-reversible` | 增量式、有开关控制、或易于删除 | 记录相关字段并接受该需求 |
| `medium` | 回滚会波及其他工作 | 呈现成本以及一个更低成本的替代方案 |
| `high-irreversible` | 公共契约、持久化数据结构、或依赖替换 | 呈现权衡取舍，并在设计前要求用户做出决定 |

若某个未知项一旦确认会将分级上调，应将其报告为阻塞性问题，而不是默认按较低分级处理。

## “伪装成方案的需求”测试

当某请求指定的是一种实现机制而非结果（例如“加一层缓存”、“引入一个队列”）时，首先判断选定该机制是否是确认当前 outcome 或范围所必需的。如果是，则只比较该决策所需的、仓库可支持的、存在实质差异的几种路径，并将该指定机制作为其中一个候选项纳入比较。如果不是，则将该机制保留为未被选定的候选项，并继续推进，不再生成其他替代方案。

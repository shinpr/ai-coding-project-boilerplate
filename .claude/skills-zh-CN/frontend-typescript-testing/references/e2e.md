# 使用 Playwright 实现 E2E 测试

检查仓库现有的浏览器测试配置、脚本、fixtures、相邻测试以及 CI 路由。保留现有的测试框架、导入方式、定位器约定、setup 生命周期、文件命名和测试位置。

当不存在浏览器测试框架时，仅在目标行为必须通过真实浏览器观察，且成本更低的现有检查无法证明该行为时，才要求浏览器级别的证据。如果需要，从仓库自身及适用的外部依据中选择足以满足需求且侵入面最小的测试框架；否则使用成本更低的可观测边界。将无法使用的执行环境报告为证明局限，而不要把它当作需要用户决定的事项。

## 测试通道选择

本工作流中的 E2E 测试分为两条通道：

| 通道 | 后端设置 | 适用模式 |
|------|---------------|-------------------|
| **fixture-e2e** | 通过 `page.route()` 或 fixture 加载器模拟；无真实服务 | 测试结构规则、定位器策略、断言内容、下方**基于 Fixture 的后端**小节 |
| **service-integration-e2e** | 使用真实服务的本地运行栈 | 上述全部内容，外加 **E2E 环境前提条件**、针对应用真实登录流程的真实认证 fixture，以及预置的测试数据 |

骨架代码中的 `@lane:` 注解声明了该测试所属的通道。据此选择对应的实现模式。

## 测试框架
- **Playwright Test**: `@playwright/test`
- 测试导入：`import { test, expect } from '@playwright/test'`

## 测试结构

### 目录布局与命名

所有内容都位于 `tests/e2e/` 下：测试文件位于其根目录，页面对象位于 `pages/`（各通道共用），fixtures 位于 `fixtures/`，fixture-e2e 使用的静态 fixture 数据位于 `data/`。

- fixture-e2e 文件：`{FeatureName}.fixture-e2e.test.ts`
- service-integration-e2e 文件：`{FeatureName}.service-e2e.test.ts`
- 页面对象：`{PageName}.page.ts`
- Fixtures：`{Purpose}.fixture.ts`
- 静态 fixture 数据：`{scenario}.fixture.json`

## 测试结构规则

- 按照三次法则抽取页面对象：首次使用时保持交互内联，第二次时可以考虑抽取，到第三次出现实质性共享交互时进行抽取。仅当共享交互本身较复杂（多步骤、需等待中间状态）或该页面已存在具有代表性的页面对象时，才提前抽取——此时应遵循该现有对象。
- 将文件中每个测试都需要的共享 setup（尤其是认证）放入 fixture，而不是在每个测试中重复这些步骤，使测试主体只包含它所验证的行为。

## 断言内容

断言用户在完成流程后可观测到的状态，而非到达该状态所经过的步骤：

- **导航** —— 断言标识目的地的 URL 或地标之一，而非把两者作为同一次跳转的独立证据分别断言。
- **渲染结果** —— 断言该流程应产出的具体内容，通过角色（role）和无障碍名称（accessible name）来标识。仅对容器进行可见性检查，只能证明容器渲染了，无法证明其中内容正确。
- **不存在** —— 当预期是某物已消失或从未出现时，应显式断言其不存在，而不是断言其他内容存在。
- **持久化效果** —— 当需求或契约声明该变更在刷新或重新导航后仍然保留时，应在那里也进行断言，因为页面内更新可能通过，而持久化却失败。对于没有此类契约的瞬时状态——筛选选择、模态框开合、向导进度——应就地断言；为这些内容添加刷新断言，等于测试了该功能从未做出的保证。

## 基于 Fixture 的后端（fixture-e2e）

fixture-e2e 测试是在真实浏览器中针对确定性的 fixtures 运行——没有真实后端，没有数据库，没有外部服务。伪造网络的方式可以是：用 `page.route()` 拦截该流程发出的每一次后端调用，并用已提交的 fixture 满足它；或者通过路由辅助函数或应用级测试模式来加载该 fixture。要拦截该流程会触达的每一次调用，而不仅仅是第一次——未被拦截的路由会悄悄命中真实网络，使测试依赖具体环境。

**fixture-e2e 的原则**：
- 后端是被伪造的，并未真实运行。执行这些测试无需运行 `npm run start:backend`
- Fixtures 在仓库中版本化（`tests/e2e/data/`），确保测试在不同机器上具有确定性
- 当流程需要已认证状态，但并不验证真实认证本身时，使用确定性的测试 cookie 或 fixture 模式的会话来建立认证状态
- 这些测试可以在 CI 中运行，无需配置外部基础设施

## E2E 环境前提条件（仅限 service-integration-e2e）

service-integration-e2e 测试需要一个正在运行、具有真实数据状态的应用程序。与 fixture-e2e 不同，环境搭建属于测试实现的范围之内。

在 service-integration-e2e 测试能够通过之前，请确认：
- [ ] 应用程序正在运行，且可通过 `baseURL` 访问
- [ ] 数据库中已有所需的种子数据（测试用户、必要记录）
- [ ] 认证流程能够使用测试凭据，针对真实认证流程正常工作
- [ ] 环境变量已设置（`E2E_*` 前缀）
- [ ] 外部服务要么可用，要么由服务级桩替代

将缺失的前提条件作为测试实现任务本身的一部分来解决；若被测行为并不需要真实运行的环境，则将该验证迁移到 fixture-e2e。

## 定位器策略

按以下顺序优先使用可访问性定位器：
1. `page.getByRole()` —— 定位无障碍角色和用户可见的名称
2. `page.getByLabel()` —— 表单元素
3. `page.getByText()` —— 可见文本
4. `page.getByTestId()` —— 最后手段；在测试中记录为何没有可感知属性能标识该元素

按 CSS id 或 class 选择会把测试与标记结构耦合，而非与用户所感知的内容耦合；应改用上述列表中的定位器。

## 视口测试

当 UI 规范定义了响应式行为时，应在 UI 规范所指明的每个视口下进行断言——既要断言该尺寸下出现的元素，也要断言该尺寸下不存在的元素，因为断点相关的 bug 通常表现为两个界面同时渲染。

## 测试隔离

- 每个测试都从一个干净的浏览器上下文开始
- 测试之间不共享状态
- 使用 `beforeEach` 处理通用设置（认证、导航）
- 对于 setup 步骤，优先使用 `page.goto()` 而非测试内导航

## 骨架注释格式

E2E 测试骨架采用与集成测试相同的注解格式，并附加一个必需的 `@lane:` 注解来声明所属通道（见上文测试通道选择）：

```typescript
// AC: [原始验收标准文本]
// Behavior: [用户操作] → [系统响应] → [可观测结果]
// @lane: fixture-e2e | service-integration-e2e
// @dependency: full-ui (mocked backend) | full-system
// Proof obligation: [该测试必须证明的边界及可观测状态]
test('AC1: [描述]', async ({ page }) => {
  // Arrange: [setup 描述]
  // Act: [操作描述]
  // Assert: [验证描述]
})
```

**按通道选择 `@dependency`**：
- `fixture-e2e` → `@dependency: full-ui (mocked backend)`（无真实服务；通过 `page.route()` 或 fixture 加载器拦截网络）
- `service-integration-e2e` → `@dependency: full-system`（需要运行中的本地运行栈）

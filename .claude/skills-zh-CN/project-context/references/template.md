# 项目上下文章节目录

定义项目上下文的章节目录以及各章节的输出结构。

## 章节索引

| 章节 | 纳入规则 | 询问问题的来源 |
|---------|----------------|-----------------------------|
| 项目概述 | 始终包含 | 本文件（如下） |
| 领域约束 | 当至少有一条规则会改变 AI 决策时包含 | 本文件（如下） |
| 质量标准 | 当至少有一条仓库特定标准会改变实现验收结果时包含 | 本文件（如下） |
| 开发阶段 | 当阶段会实质性改变 AI 行为时包含（例如为原型阶段抑制测试脚手架） | 本文件（如下） |
| 目录约定 | 当存在非显而易见的文件放置规则时包含 | 本文件（如下） |
| 外部资源 | 当项目依赖仓库之外的资源时包含（设计来源、Schema 来源、密钥存储、IaC 来源等） | `external-resources-{frontend,backend,api,infra}.md`（仅加载与项目相关的领域） |

## 章节定义

### 项目概述

**纳入条件**：始终。

**询问**：
- AskUserQuestion 1：“这个项目是做什么的？（1-2 句话）”
- AskUserQuestion 2：“它属于哪个领域？”，并从常见类别中给出具体选项示例（例如开发者工具、金融科技、医疗健康、电子商务、内部平台）。始终包含“其他”。

**输出结构**：
```markdown
## 项目概述
- **本项目用途**：<一到两句话>
- **领域**：<领域>
```

### 领域约束

**纳入条件**：当至少有一条约束在被忽略时会导致 Bug 或合规问题时包含。

**询问**：
- AskUserQuestion：“在本项目中做决策时，AI 必须遵循的领域特定规则有哪些？”选项：“有，我来列出” / “没有适用的领域约束”。
- 当选择“有”时：对每条规则（上限 3 条），采集规则陈述以及一个可衡量的检查项。仅在陈述能以通过/不通过来评估时才接受；将主观表述重新表述为可衡量的形式（例如把“注意 PII”改写为“日志输出使用匿名化的患者 ID”）。
- 根据项目概述中采集到的领域来调整示例表述（例如金融科技领域：“每笔资金变动都会追加一条审计日志条目”；开发者工具领域：“生成的代码保持锁文件命令可调用”）。

**输出结构**（若约束数为零则完全省略本章节）：
```markdown
## 领域约束
1. <可衡量的规则 1>
2. <可衡量的规则 2>
3. <可衡量的规则 3>
```

### 质量标准

**纳入条件**：当本仓库强制执行至少一条超出通用语言或框架指南、会改变实现是否被验收的标准时包含。

**询问**：
- AskUserQuestion：“是否存在仓库特定的质量标准，智能体应在实现和评审阶段都应用？”选项：“有，请根据仓库依据提出建议” / “有，我来提供” / “没有适用的仓库特定标准”。
- 仅根据用户提供的策略，或由仓库指令、贡献者文档、CI、清单和脚本、Schema 与公共契约、测试或有代表性的实现模式所表达或强制执行的验收条件来构建建议。仅在支持性或矛盾性依据可能改变某条建议的适用性、采纳状态或本仓库归属关系时才对其进行核查。
- 仅当某条建议不满足会改变实现验收结果时才保留它。为其赋予尽可能狭窄且有用的**适用条件（Applies when）**、一条正向且可观测的**通过条件（Pass）**，以及作为**依据（Evidence）**支持该建议的仓库引用或用户确认的策略。合并会产生相同失败与修正结果的建议；省略所需依据不可得的建议，并报告缺失内容。
- 对于更新操作，询问哪些标准需要变更，并原样保留其余所有标准。在采集之前，展示提议的新增、变更和移除内容以及未变更的剩余部分，展示支持或反驳每项变更的依据，并获得用户的明确确认。

**输出结构**（若最终标准数为零则完全省略本章节）：
```markdown
## 质量标准

### <简洁的标准名称>
- **适用条件**：<可观测的适用条件>
- **通过条件**：<正向可观测的验收状态>
- **依据**：<仓库路径与章节、标识符、契约，或用户确认的策略>
```

### 开发阶段

**纳入条件**：当阶段会实质性改变 AI 行为时包含。当各阶段行为相同时跳过。

**询问**：
- AskUserQuestion：“本项目处于哪个阶段？”选项：“原型（Prototype）”、“生产（Production）”、“运行中（In operation）”、“各阶段之间无实质差异”。
- 当选择“各阶段之间无实质差异”时：省略本章节。

**输出结构**：
```markdown
## 开发阶段
- **阶段**：<原型 | 生产 | 运行中>
```

### 目录约定

**纳入条件**：当至少存在一条从仓库结构看并非显而易见的文件放置规则时包含（即，一个查看目录树的贡献者会猜错）。

**询问**：
- AskUserQuestion：“是否存在 AI 应遵循的文件放置规则？”选项：“有” / “没有”。
- 当选择“有”时：将每条规则采集为单行，说明触发条件与目标位置（例如“临时工作文件：放置于 `./tmp/` 下，并在完成后删除”）。

**输出结构**（若规则数为零则完全省略本章节）：
```markdown
## 目录约定
- <规则 1>
- <规则 2>
```

### 外部资源

**纳入条件**：当至少有一个被选中的领域存在一个现存的轴（axis）或非空的自我声明时包含本章节。否则省略本章节。

**询问路由**：
- AskUserQuestion：“本项目适用哪些外部资源领域？”多选选项：
  - 前端（设计来源、设计系统、指南、可视化验证环境）
  - 后端（数据库 Schema、迁移历史、密钥存储、后台任务）
  - API 契约（Schema 来源、Mock、认证、Schema 变更流程）
  - 基础设施（IaC 来源、环境配置、基础设施密钥、部署触发方式）
  - 均不适用
- 对每个被选中的领域，使用下方的 slug 映射表加载对应的引用文件，并运行其询问协议。

**领域到文件 slug 的映射**：
| 领域（面向用户的标签） | 引用文件 |
|---------------------------|----------------|
| 前端 | `external-resources-frontend.md` |
| 后端 | `external-resources-backend.md` |
| API 契约 | `external-resources-api.md` |
| 基础设施 | `external-resources-infra.md` |

**询问协议**（针对每个领域引用文件）：每个引用文件定义了若干结构化的轴，以及一个自我声明阶段。结构化阶段对每个轴提出一个 AskUserQuestion，并将“不适用”作为一个明确选项提供。自我声明阶段始终会运行一次，询问自由形式的补充内容，无论结构化选择的结果如何。

**每轴输出 Schema**（3 个字段）：
```markdown
#### <轴名称>
- 来源类型：<用户所选 AskUserQuestion 选项的原文文本>
- 位置：<URL | 文件路径 | 服务或包名>
- 访问方式：<WebFetch | 文件读取 | MCP 服务器名称 | CLI 命令 | 人工操作流程>
```

**轴输出规则**：

1. **轴的输出取决于 Schema 是否可被填充。** 当用户的选择指向一个拥有可识别的**位置**和**访问方式**值的外部资源时，渲染该轴的内容块。以下选择会使该轴产生零行输出：
   - 已列出的表示“不存在”的选择：“不适用”、“没有<资源>”、“不需要<资源>”、“没有文档化的<资源>”、“临时性<资源>”、“人工<流程>（无<资源>）”。
   - 任何其“位置”和“访问方式”值解析为空白的其他选择。

2. **同一轴内的多个实例**（例如主数据库与分析数据库、CSS 和无障碍分别对应不同的指南文件）——重复该轴的内容块，并添加区分性后缀：
   ```markdown
   #### 数据库 Schema 来源 — Primary
   - 来源类型：仓库内的 Schema 文件
   - 位置：prisma/schema.prisma
   - 访问方式：文件读取

   #### 数据库 Schema 来源 — Analytics
   - 来源类型：对实时数据库执行内省的数据库 MCP 服务器
   - 位置：bigquery-prod
   - 访问方式：MCP 服务器 `bigquery`
   ```

3. **跨轴引用**（例如同一个密钥存储同时出现在后端和基础设施下）——首次出现时携带规范字段；第二次出现时渲染为对首次出现处的引用：
   ```markdown
   #### 基础设施中的密钥
   - 来源类型：通过 IaC 数据查询从密钥管理器获取的密钥
   - 引用：与“后端 > 密钥存储”相同
   - 访问方式：<继承；仅记录差异（如有）>
   ```

**领域内容块布局**：
```markdown
### <领域>

<按目录顺序排列的轴内容块，均按照上述规则渲染>

#### 其他资源

<仅在自我声明阶段采集到内容时渲染；置于同一领域中最后一个存在的轴之后>
- <用户提供的自由形式描述>
```

## 输出组装规则

询问完成后，按照章节索引的顺序组装配置好的 `SKILL.md`。该目录规定上述各章节的内容形态以及以下跨章节规则：

1. 被标记为省略的章节产生零行输出。重建后的正文将直接推进到下一个被纳入的章节。
2. 外部资源中的领域内容块按目录顺序出现（前端 → 后端 → API 契约 → 基础设施），无论用户在询问过程中选择它们的顺序如何。
3. 对每个 `add` 和 `update` 章节应用以下询问阶段过滤器：当用户提供的规则使用主观表述时（例如“注意性能”），追问：“AI 要如何验证这条规则是通过还是不通过？请将其改写为可度量的检查项，或回复 `drop` 以省略。”以可度量形式给出的规则原样采用；主观的规则替换为用户改写后的版本，用户回复 `drop` 时则省略该规则。采用的规则通过常规章节输出方式写入；该过滤器本身不产生输出。

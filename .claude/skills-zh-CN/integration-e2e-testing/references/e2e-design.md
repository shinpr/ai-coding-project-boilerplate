# E2E 测试设计（浏览器测试框架）

本参考文档全文以 Playwright 作为默认示例，因为它是这些工作流所假定的标准 E2E 浏览器测试框架。若项目选用了不同的框架（Cypress、Selenium 等），可调整具体模式，但证明边界规则保持不变。

## 两条 E2E 通道

本工作流中的 E2E 测试分为两条通道（参见父技能的“测试类型与选择”）：

| 通道 | 适用场景 | 证明边界 | 成本 |
|------|----------|----------|------|
| **fixture-e2e** | 使用确定性 fixture（模拟后端 / fixture 数据）验证 UI 流程 | 真实浏览器是判定边界；后端行为以 fixture 状态提供 | 在 CI 中配合 fixture 设置运行 |
| **service-integration-e2e** | 流程正确性依赖真实的跨服务行为（数据持久化、事务一致性、外部契约） | 正在运行的服务边界本身就是判定内容的一部分 | 设置与维护成本更高；仅当该边界能唯一暴露问题时才选用 |

两条通道通常都使用 Playwright，区别在于后端是模拟 / fixture 驱动的，还是真实运行的。

## 何时创建 E2E 测试

E2E 候选项针对跨越多个页面或需要真实浏览器交互的**关键用户流程**。应根据验证是否需要真实服务来选择通道。

### 候选项属性

E2E 候选项是具备以下任一属性的行为，无论约束性产物在何处记录该行为：

| 属性 | 为何构成 E2E 候选项 |
|------|----------------------|
| 跨越多个界面 | 承诺的结果只有在经过一系列界面跳转后才可观测 |
| 需要真实浏览器 | 导航、cookie、存储或实际 DOM 渲染决定了结果 |
| 状态只能通过导航到达 | 无法在进程内产生的错误、空状态或加载状态 |
| 交互依赖浏览器 | 拖放、键盘导航或响应式行为 |

将约束性产物映射到这些属性；本技能不指定具体的产物章节名称。

### 选择标准

**包含**：
- 多页面用户流程（登录 → 仪表盘 → 操作 → 确认）
- 需要真实浏览器 API 的流程（导航、cookie、localStorage）
- 需要实际 DOM 渲染的可访问性验证
- 跨视口的响应式行为

**以下情况改用集成测试**：
- 测试单个组件的状态变化 → 使用进程内组件渲染器（React/TS 使用 RTL）
- 测试 API 响应处理 → 使用进程内 API mock + 组件渲染器（React/TS 使用 MSW + RTL）
- 测试纯数据转换 → 使用单元测试

## 候选项记录

以此表单记录每个已选中的候选项，以便下游实现能够保留证明决策。

### 映射模板

```
Screen Transition: [界面 A] → [界面 B] → [界面 C]
AC Reference: AC-{id}
User Journey: [用户完成的操作描述]
Lane: fixture-e2e | service-integration-e2e
Preconditions: [认证状态、数据状态 —— 注明是 fixture 驱动还是真实数据]
Verification Points:
  - [每一步需要断言的内容]
Primary Failure: [该测试必须能捕获的回归]
Proof Obligation: [该测试必须覆盖的边界与可观测状态]
```

**通道决策**：默认选择 `fixture-e2e`。当验证需要观测真实的跨服务行为时（例如测试断言数据经真实数据库写入后仍持久存在，或外部服务收到了正确的负载），才切换到 `service-integration-e2e`。

## Playwright 测试架构

### 页面对象模式

通过页面对象组织浏览器交互，以提高可维护性：

```
tests/
├── e2e/
│   ├── pages/                       # 页面对象（跨通道共享）
│   ├── fixtures/                    # 测试 fixture 与辅助函数（认证、数据填充）
│   ├── data/                        # fixture-e2e 使用的静态 fixture 数据
│   ├── *.fixture-e2e.test.ts        # fixture-e2e 测试文件
│   └── *.service-e2e.test.ts        # service-integration-e2e 测试文件
```

### 测试隔离

- 每个测试都从一个干净的浏览器上下文开始
- 测试之间不共享状态
- 使用 `beforeEach` 处理通用设置（认证、导航）
- 设置阶段优先使用 `page.goto()`，而非在测试内部导航

### 视口测试

当 UI 规范定义了响应式行为时，测试关键断点：

| 断点 | 宽度 | 何时测试 |
|------|------|----------|
| Mobile | UI 规范断点或已配置的 mobile 项目视口 | 若 UI 规范定义了移动端专属交互 |
| Tablet | UI 规范断点或已配置的 tablet 项目视口 | 若 UI 规范定义了平板端的布局差异 |
| Default | Playwright 项目视口或 UI 规范基线 | 针对每个已选中的响应式流程 |

## 最小集合检查

- 每个产出的 E2E 测试都覆盖一个已采纳的证明义务，且该义务没有被更廉价的测试证明过。
- 每个被省略的 E2E 候选项，都已在别处覆盖、与其他场景重复，或不需要浏览器 / 系统边界。
- 当一个连贯的流程能证明多个义务、且每个断言仍可追溯到其对应失败时，优先选用该流程。
- 由不同的实质性失败决定测试数量；保留能覆盖所有失败的最小集合。

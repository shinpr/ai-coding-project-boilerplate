# Lite 模式

Lite 模式减少中间验证调用，同时保留已确认的成果、用户批准停止点、权限边界、实现检查和完成依据。解析出的模式决定配方中适用的调用及其结果条件。

## 调用集合

| 调用 | Lite 模式下的行为 |
|---|---|
| code-verifier | 省略。下游使用方不会收到此调用产生的 `verification_evidence` 或 `prior_layer_verification`。 |
| design-sync | 省略。后续批准停止点在前一个保留的步骤之后执行。 |
| security-reviewer | 从实现后评审集合中省略；code-reviewer 仍运行。 |
| 工作计划任务集合中逐任务的 quality-fixer | 替换为下方的最终质量检查。受理执行者结果及必需的集成/E2E 评审后，在配方已有的提交点提交已完成任务。 |

省略的调用不会提供可解释、复核或报告为通过的结果。报告明确说明哪些验证在 Lite 模式下被省略。用户指定的专家评审仍是请求的成果，无论默认调用集合如何均须执行。

Small 及其他单循环流程保留 quality-fixer，因为该调用本身已是最终执行。评审修正的质量检查和必需的集成/E2E 测试评审仍适用。

## 最终质量检查

在最后一个任务提交之后、实现后评审之前，对每个存在已完成任务的层调用一次相应的 quality-fixer。传递其既有输入：

- `direct_scope`：工作计划的成果与排除项、该层已完成任务文件的路径和已变更实现路径，以及所有这些任务的 Operation Verification Methods。将已提交任务的变更纳入此范围。
- `qualityCommand`：调用方、约束来源或仓库配置提供时，传递该权威质量命令。

通过“专家结果受理”受理结果。对于 `stub_detected`，将每个 `incompleteImplementations` 条目原样路由给其所属任务的执行者，受理其实现结果及必需的测试评审结果，然后重复最终质量检查。

产生的修正获得适用的质量结果后，在配方已有的提交边界提交。按正常完成流程记录保留的验证局限。评审后的变更仍接受适用的质量检查；在后续变更使依据失效之前，复用有效依据。

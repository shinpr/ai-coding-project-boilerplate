# 评审裁定（Review Resolution）

当交付物评审者或验证者返回可路由至修正或推进的发现结果时，使用此协议。作为下游专家证据使用的验证输出仍属于该专家交接的一部分。

保持评审者/验证者的证据归属，使每个检查点都收敛到约束来源；编排者重新解释会产生未经评审的需求，并使批准或复核无法终结。

## 评审结论条件

按以下顺序路由 document-reviewer 的结果：

- 无论问题集如何，`rejected` 结论都先通过来源优先级、父工作流的“需求变更检测”或不可逆操作授权条件来解决约束来源冲突，然后才能进行下一次评审
- 可处理的发现项集合为空时即完成评审；下游使用方仅接收已评审的产物路径和已有的约束来源证据
- 可处理的发现项集合非空时进入第 1 节

在 `rejected` 优先级之后，当 `approved` 或 `needs_revision` 与问题集不一致时，以问题证据主导路由。已完成的评审不会产生作者修正或下游语义输入。

对于 verifier、design-sync、code-reviewer、security-reviewer 和 integration-test-reviewer 的结果，只有其调用方契约路由至修正的状态或发现才进入第 1 节。

使用结果产出者所声明的验证模式：

- **复核型评审者**：document-reviewer、code-reviewer、security-reviewer 和 integration-test-reviewer 接受 `prior_feedback`，并在修正后返回 `prior_feedback_reconciliation`
- **独立重跑验证者**：code-verifier 和 design-sync 每次都根据原始输入独立报告当前状态。依据其结果应用修正后，重新运行该验证者并判定当前结果；仅有拒绝（decline）的结果即为完成

## 1. 评估每个发现

在分配处置方式之前，检查当前交付物的相关部分、引用的仓库证据以及约束来源，把评审者的断言当作需要核实的证据来对待。

当证据表明已确认的成果、目标状态需求与非目标无法同时成立、且需要用户来选择改变哪个价值边界时，离开评审裁定并应用父工作流的“需求变更检测”。当修正需要为不可逆的外部操作获得授权时，离开评审裁定并应用父工作流的不可逆操作授权条件。这些工作流停止点不是发现的处置方式。

编排者为每个可处理的发现项指定一种处置方式：

| 处置方式 | 使用场景 |
|---|---|
| `apply`（应用） | 若不修改当前交付物将阻止实现已确认的成果、违反约束性需求、设计决策或仓库规则、使所需的正确性或验证缺乏支撑，或将下游工作绑定到总体复杂度缺乏当前证据支持的设计增量。 |
| `decline`（拒绝） | 若不修改当前交付物仍能实现已确认的成果，并满足约束性条件及所需的正确性与验证；而该发现实际上提议的是新增范围、反转某项排除项、可选的加固或通用清理、重复的证明、依赖于评审者所声明的产物边界之外的属性，或涉及该边界之外的其他工作。 |

当修正能保持已确认的价值边界不变时，已确认的安全风险、实现偏差或约束来源矛盾应被赋予 `apply`；仅成本因素不改变该分类。当这些边界保持成立时，技术设计、契约或实现方面的变更属于修正工作，而非用户决策。

为每个发现项记录：

- 稳定的发现 ID；
- 处置方式；
- 约束依据与具体证据；
- 若为 `decline`，记录理由

处置方式决定路由方向。对于 `apply`，原样转发完整的评审者发现对象，保留每个字段和值，仅额外添加 `apply` 处置方式。这种逐字转发使修正立足于已评审的证据；编排者撰写的转述或补充会成为未经评审的需求。作者或执行者依据约束来源和当前仓库证据来决定具体修正方案。

只有具有 `apply` 处置方式的发现，以及第 3 节下持续保持 `apply` 的发现，才会进入作者或执行者交接环节。

## 2. 修订与再考量

根据每个发现所要求的已接受状态，选择现有的修正责任方：

- 当实现已满足已确认的价值边界、而技术性产物需要变更时，使用负责该文档的作者；
- 当实现本身需要变更以达到已接受状态时，使用执行者

对于混合的发现集，先完成作者负责的修正，再针对修正后的约束性产物重新评估执行者负责的发现。将完整的 `apply` 发现对象及其处置方式原样传递给所选的责任方。将文档作者调用为一次针对原始目标的新更新调用；产物本身会补充未受影响的上下文。使用执行者时，保留其原始的 `task_file` 或四个直接范围字段，并将发现作为 `correction_findings` 添加；修正仍在原执行范围之内。

对于处置为 `apply` 且涉及未经验证、会改变决策的前提的 Design Doc 发现项，全新的 technical-designer 调用会应用“评审触发的有界自我验证”。该发现项携带确切的前提及所需证据；设计者选择现有证据、一个在所有未解决结果下均有效的更小设计方案，或者在所有适用条件成立时使用探测方式。修正后重新运行发起验证的验证者或评审者。

对于复核型评审者，复用最初的评审者输入，并添加 `prior_feedback` 作为一个由 `{ id, disposition, reason?, evidence }` 组成的数组。

修正评估的范围严格等于所收到的每一项。评审者完成该范围后：

- 当当前证据表明产物满足该发现并保持已改变的边界时，将已应用的项标记为 `resolved`；否则将该项标记为 `maintained`，并引用当前证据；
- 当当前证据和约束来源不再支持某个已拒绝的发现时，将其标记为 `withdrawn`；否则将该项标记为 `maintained`，并引用当前证据；
- 为收到的每个 ID 恰好发出一条 `prior_feedback_reconciliation` 记录

仅从这些复核记录中推导出修正复评的状态或结论。独立的事实性验证者可能会重复观察到同一处差异；由编排者依据约束来源证据来赋予其处置方式。

对于独立重跑验证者，在依据其最新结果应用至少一项修正后，或当调用方的重跑规则要求提供当前状态结果时，重新运行验证者。最新结果替代已修正项此前的当前状态结果。当最新结果所报告的断言或冲突在实质上相同、且约束来源证据未变时，保留此前的拒绝结论；在路由之前先判定新的或有实质变化的发现。应依据断言/冲突本身及所引用的来源/目标证据来匹配实质上相同的发现，而不仅依赖重新生成的位置性 ID。

## 3. 收敛或报告

根据所记录的 `prior_disposition` 来解决修正复评条目：

- `resolved` 与 `withdrawn` 即为完成；
- `prior_disposition: apply` 的 `maintained` 项，通过相同的作者或执行者通道原样返回原始发现和完整的复核条目，随后再进行一次修正复评；
- `prior_disposition: decline` 的 `maintained` 项保留该拒绝结论，不重新开启修正循环

对于独立重跑验证者，具有 `apply` 的当前发现通过修正路径返回，具有保留或新赋予的 `decline` 的当前发现即为完成，可处理的发现项集合为空时即为完成。

当同一个 `apply` 发现在连续两次修正尝试后仍然存在，则将修正循环标记为未完成，并连同其最新的实现与验证证据一并报告该发现。对于经范围内恢复后仍不可用的所需输入或验证前提，也适用相同的终结报告方式。当每个 `apply` 修正均已完成、且所有其他可处理的发现项的处置方式均为 `decline` 时，即可推进。父级的“需求变更检测”和不可逆操作授权条件独立控制各自的工作流停止点。

交接内容恰好包含以下集合：

- 原始评审目标标识符；
- 复查时保持不变的最初评审者或验证者输入；
- 完整的 `apply` 发现对象原样呈现，仅额外添加编排者的处置方式；
- 当某个保持 `apply` 的发现返回给其作者或执行者时，附上完整的复核条目；
- 当下游使用方接收评审者的复核结果时，在 `prior_feedback` 中附上被拒绝的 ID 及其理由和证据；对于独立重跑验证者，将这些处置方式保留在编排者状态中，并按上述方式与最新结果进行比对

作者交接内容中不包含任何其他由编排者撰写的语义性内容。

最终的用户报告列出处置为 `decline` 的每一项可处理的发现项，包括其 ID、约束理由和证据。

## 已解决的验证证据

在针对 code-verifier 输出完成评审裁定后，向下一个 document reviewer 传递一个 `verification_evidence` 对象：

- 在每次应用修正并重新运行之后，从最新的验证者结果开始；
- 保持其 `summary`、`inventoryCoverage` 和 `limitations` 不变；
- 保持每个剩余差异项不变，并为其添加 `disposition`，若为拒绝（decline），再添加 `dispositionReason` 和 `dispositionEvidence`；
- 仅在每个剩余差异项均带有已解决的 `decline` 处置方式后才将其纳入；已应用的修正由最新的验证者结果来体现

文档评审者会使用这份已解决的证据，但并不负责验证者处置方式的收敛。当被评审的证据就是当前验证者结果时，更新和逆向工程流程可以在修正解决之前，将该结果作为 `verification_evidence` 传递。

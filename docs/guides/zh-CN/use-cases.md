# 使用场景和命令

如果项目尚未配置，请从[快速开始](./quickstart.md)入手。本页将常见的开发目标映射到负责该目标的命令。

## 选择命令

### 实现和调查

| 命令 | 目标 |
|---|---|
| `/implement <request>` | 确认需求并完成适用的设计、实现、验证和提交工作流 |
| `/task <request>` | 确定范围和适用技能后，执行一个聚焦任务 |
| `/diagnose <problem>` | 调查问题、独立验证原因并推导有依据的解决方案，但不实施其中任何一个 |
| `/review [Design Doc]` | 评审已完成的后端或通用实现，确认其符合约定的目标、仓库标准和安全边界，并应用用户批准的修正 |
| `/front-review [Design Doc]` | 对前端实现运行相同的评审和修正流程 |

### 设计和计划执行

| 命令 | 目标 |
|---|---|
| `/design <request>` | 确认范围、解决符合条件的 ADR 决策，并生成批准的设计文档 |
| `/front-design <request>` | 在 UI 决策仍未确定时添加 UI 规范，然后生成批准的前端设计文档 |
| `/plan [Design Doc]` | 创建、评审并批准工作计划；必要时可先生成集成或 E2E 测试骨架 |
| `/front-plan [Design Doc]` | 创建并批准前端工作计划 |
| `/build [Work Plan]` | 根据已批准的计划生成并执行后端或通用任务文件 |
| `/front-build [Work Plan]` | 根据已批准的计划生成并执行前端任务文件 |
| `/add-integration-tests [Design Doc]` | 在现有代码中添加证明已接受行为所需的最小集成或 E2E 测试集 |
| `/reverse-engineer <path>` | 发现现有行为，生成经过评审的 PRD 和可选设计文档 |
| `/update-doc [document]` | 更新并评审现有 PRD、ADR 或设计文档，但不继续实现 |

### 项目知识和技能

| 命令 | 目标 |
|---|---|
| `/project-inject` | 将项目特有的前置信息和质量标准记录到 `project-context` |
| `/create-skill <knowledge>` | 通过交互式问答和评审创建新技能 |
| `/refine-skill <change>` | 对现有技能进行针对性修改并评审结果 |
| `/sync-skills` | 技能内容发生变化后同步技能元数据 |

## 常见流程

### 完成一次变更

```text
/implement 添加 webhook 签名验证
```

当一个请求需要完成完整生命周期时使用 `/implement`。它会先确认目标和排除项，再根据仓库依据选择最小的文档和实现路径。

### 执行一个聚焦任务

```text
/task 修复包含“+”的电子邮件地址验证
```

当请求已经具有单一、聚焦的目标，并且不需要完整的设计到构建工作流时，使用 `/task`。

### 在选择修复方案前进行诊断

```text
/diagnose 更新后，请求偶尔返回旧数据
```

`/diagnose` 会报告经过验证的原因和有依据的解决方案选项。选择解决方案后，请另行给出实现指令。

### 分离设计、规划和实现

```text
/design 添加 webhook 签名验证
/plan docs/design/webhook-signature-design.md
/build docs/plans/20260809-feature-webhook-signature.md
```

如果每个持久文档都应在继续前单独获得批准，或者计划中的工作将在另一个会话中执行，请使用这些独立命令。

### 继续现有的计划工作

```text
/build
```

不带参数时，`/build` 会解析该工作流拥有的可消费任务集。如果可能对应多个计划，请传入工作计划路径。对于执行通道为前端的任务条目，使用 `/front-build`。

### 评审已完成的实现

```text
/review docs/design/webhook-signature-design.md
```

该命令会评审已完成的实现，确认其符合约定的目标和仓库标准，没有不必要的改动，也没有功能、可靠性或安全方面的严重问题。它会列出有依据的问题，仅应用用户批准的修正，修正后再次检查这些问题，并在评审收敛后运行一次最终质量检查。它不会为评审修复创建任务文件。

## 文档路由

| 结构规模 | 条件 | 持久文档 |
|---|---|---|
| 小型 | 一个完整目标在单一职责边界内有一条明确、受仓库支持的实现路径 | 无 |
| 中型 | 一个完整目标需要协调某个边界，或包含可能长期保留的选择 | 设计文档 → 工作计划 |
| 大型 | 多个可独立产生价值的目标需要分别进行设计决策 | PRD → 设计文档 → 工作计划 |

文件数量只是变更范围的依据，不是规模判断规则。

- 只有当至少存在两个可信且实质不同的选项，并且该选择具有长期影响时，技术议题才会生成 ADR。ADR 集合会在设计文档之前获得批准。
- 只有在界面、状态、交互或视觉决策仍未确定时，前端或全栈工作才会生成 UI 规范。
- 小型工作会将已确认的目标、约束依据、受影响路径和可观察的验证方式直接交给实现，不会创建占位文档或任务文件。

## 测试和质量行为

- 集成或 E2E 测试骨架根据已接受行为和证明义务进行选择。只有当现有测试覆盖相同边界，并能在所防范的重要故障发生时失败，它才算作有效证明。
- 如果断言仍能清晰映射到各个故障，一个场景可以证明多项义务。设置不同或故障模式不同的场景应保持分离。
- `quality-fixer` 会运行从仓库配置和任务验证方法中发现的检查，修复由当前变更造成的失败，并记录无法运行的检查或与变更无关的基线失败。
- 质量结果不会声称无法运行的检查已经通过。构建和评审完成报告会保留这一限制。

## 文档生命周期

- PRD、ADR、UI 规范和设计文档是长期保留的约束依据。
- 工作计划保存已批准的实现顺序和任务边界。
- 生成的任务文件是执行交接材料。构建工作流会在提交相应工作后删除已消费的任务文件。

## 自定义项目行为

使用 `/project-inject` 记录适用于整个仓库的事实、约束和质量标准。对于只应在某一特定职责下加载的可复用判断，请使用技能。不要将特定功能的决策复制到全局规则中；应将其保存在相应的 PRD、ADR、UI 规范或设计文档内。

修改技能内容后运行：

```text
/sync-skills
```

有关信息放置和验证方法，请参阅[技能编辑指南](./skills-editing-guide.md)。

`.claude/commands/` 下的命令定义是详细执行行为的事实来源。

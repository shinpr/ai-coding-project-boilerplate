# 技能编辑指南

只有当一个能力足够的模型无法仅凭基础知识和仓库安全地做出某项决策时，技能才应改变该决策。请保留严格的边界和依据要求，同时允许模型在这些边界内选择可逆的路径。

## 判断是否需要技能

仅当以下条件全部成立时，才应将规则保存在技能中：

- 同一职责下会反复出现该决策；
- 项目、产品或组织依据会改变正确选择；
- 该信息尚未由代码、配置或约束文档负责；
- 删除该规则会改变决策、下游结果、不可逆边界或可观察的验证结果。

通用编程知识、单次变更的设计决策、说明性背景，以及仅用于防止模型过去某种习惯的规则，本身都不足以证明需要创建技能。

## 将信息放入其负责位置

| 信息 | 负责位置 |
|---|---|
| 真正适用于所有任务和会话启动的规则 | `CLAUDE.md` |
| 仓库用途、领域约束、质量标准、目录约定和外部依据访问方式 | 通过 `/project-inject` 写入 `project-context` |
| 针对某项技术或工作流职责的可复用决策标准 | 技能 |
| 单次变更的产品目标、已接受需求和排除项 | PRD 或已确认的需求记录 |
| 在可信选项之间作出的、会对后续工作产生长期影响的技术选择 | ADR |
| 特定功能的职责、契约、流程和验证边界 | 设计文档或 UI 规范 |
| 实现顺序和可执行任务边界 | 工作计划 |
| 包脚本、schema、路由和运行时配置 | 仓库中各自的源文件 |

请说明如何找到现有来源，而不要将其复制到技能中。只添加来源本身无法表达的解释规则。

## 提供决策依据，而不是预测好的路线

每项职责应提供以下四类信息：

| 输入 | 回答的问题 |
|---|---|
| 目的 | 这个技能负责什么结果？ |
| 依据 | 哪些需求、仓库事实或检查可以改变决策？ |
| 选择标准 | 智能体如何根据这些依据选择下一步？ |
| 最小结果 | 下一个使用者所需的最小结果是什么？ |

“运行所有测试通道”是在预先规定工作。“使用能够暴露所需边界的最窄测试”则提供了选择标准。一个能力足够的模型可以根据仓库依据选择通道，无需为每种框架或项目结构预先定义分支。

### 边界约束

边界约束描述必须始终成立的条件：

- 实现已确认的目标，并保留记录的排除项；
- 除非获得授权的需求明确变更，否则保留公共契约；
- 不可逆的外部操作必须获得相应权限；
- 只有在所需行为可观察时才声明完成。

这些约束即使在模型能力提升后仍然有意义。

### 产生工作的约束

产生工作的约束会不考虑当前需要，直接要求创建文档或执行操作，例如固定的备选方案数量、强制测试通道、通用缓解记录、固定重试循环，以及在人类阅读的文档中使用精确标签。

仅当当前依据表明所生成的工作能够保护某项需求、使用者或可观察故障时，才保留此类约束。否则，请将其替换为仅在需要时选择该工作的决策标准。

在软件解析结果的地方使用精确 schema。对于人类阅读的文档，除非下游使用者需要特定表示，否则应接受语义等价的依据。

让模型自行解决仓库内部且可逆的歧义。只有在继续工作需要改变产品目标、公共契约、已批准的主要设计、用户持有的权限或不可逆操作时才询问用户。对于危险的操作边界，应尽可能使用权限、沙箱、隔离凭据和其他机械控制；提示词本身不能构成隔离措施。

## 使用渐进式披露

```text
.claude/skills/api-contracts/
├── SKILL.md
├── references/        # 按需加载的详细标准
└── scripts/           # 由技能负责的确定性操作
```

### 元数据

`description` 是技能选择的依据，而不是目录。它应说明职责、该职责对项目的特有价值，以及应触发此技能的用户表达。

```yaml
---
name: api-contracts
description: 应用本项目共享的 API 兼容性与错误语义。创建或修改 HTTP 端点或共享 API 类型时使用。
---
```

如果一个技能只描述基础知识，它要么需要加入项目特有内容，要么根本不需要存在。

### SKILL.md 正文

只使用该职责确实需要的章节。一个实用的顺序是：

1. 目的和范围；
2. 来源和必需输入；
3. 决策标准；
4. 有顺序要求时的依赖流程步骤；
5. 实际使用方所需的输出格式（如有）；
6. 验证方式和未解决输入的处理；
7. 参考资料。

只保留包含实际操作内容的章节。先写常见决策路径，再写例外情况。依赖流程步骤应说明完成依据，以及允许进入下一步的条件。

### 参考资料和脚本

- 从 `SKILL.md` 直接链接支持文件，避免形成多层参考链。
- 先压缩内容；仍然需要的条件性资料再放入 `references/`，并且只加载控制当前决策的部分。
- 当同一确定性操作本来会被反复生成时，将其放入 `scripts/`。
- 如果现有模板或脚本已经能够生成所需文档，请复用它。
- 将外部 schema、API 或基础设施的访问方式记录在 `project-context` 中；仅有 URL 并不能保证每个执行环境都能访问。

## 使用 BP-001 到 BP-009 进行评审

使用与 [rashomon](https://github.com/shinpr/rashomon) 相同的九项检查：

| 模式 | 技能检查 |
|---|---|
| BP-001 否定式指令 | 先说明所需行为。只针对狭窄且不可逆的边界保留明确禁令，并同时给出安全替代方案和授权条件。 |
| BP-002 模糊指令 | 仅澄清会实质改变正确性、范围、下游用途或验证结果的歧义。使用限制最少但足够的标准。 |
| BP-003 缺少输出格式 | 只定义实际输出使用者需要的字段、顺序或序列化方式。 |
| BP-004 内容缺乏结构 | 添加能够体现优先级、角色和依赖关系的最小结构。简单规则可以保持为普通文本。 |
| BP-005 上下文缺失或过多 | 只保留会改变决策、操作或验证结果的上下文，并指出项目特有的来源。 |
| BP-006 流程控制缺失或过多 | 只为真实依赖、权限、不可逆操作、机器读取的契约和完成证明保留检查点。对于可逆选择，应提供目的、依据和选择标准，而不是规定路线。 |
| BP-007 不必要的示例 | 优先使用规则或使用者要求的格式。只为不明显的项目映射、例外或边界添加最小示例集。 |
| BP-008 缺少不确定性处理 | 区分已观察事实、推断和未知项。只有在未知项阻塞下一步转换时才停止，并指出缺少的具体依据或用户决策。 |
| BP-009 无边界地产生工作 | 将新发现视为候选项。只保留目标、边界、真实使用者或必要证明所需的工作，并允许不做变更、复用和有依据地拒绝。 |

示例不仅会影响它直接说明的事实，还会固定格式、局部命名方式和可能的解决方案。如果可以用简洁规则消除歧义，请删除相应示例。

## 创建或修改技能

尽可能使用仓库提供的命令：

```text
/create-skill 定义本项目使用的 API 兼容性规则
/refine-skill 从 api-contracts 中删除按文件数划分的阈值，改为依据实际使用者
/sync-skills
```

对于手动修改或需要评审的变更，请使用三个检查点：

1. **分析** — 保留预期目标和需求；检查完整技能及其必需参考资料；扫描 BP-001 到 BP-009；找出错误的决策或输出。
2. **优化** — 在负责该问题的规则中解决每个有依据的问题；只有当一项约束能够消除影响目标的歧义或保护已明确的需求时才添加它。
3. **平衡** — 验证意图保留、决策充分性、信息密度、约束必要性、工作量相称性和可追溯性；删除不会改变任何决策或有效输出的新增内容。

编辑后，运行 `/sync-skills` 和仓库的技能索引检查。

## 审核每条规则

在保留或添加规则前，请询问：

1. 删除该规则后，哪个决策、边界、使用者或可观察故障会发生变化？
2. 该规则是在限制范围，还是不考虑需要而制造工作？
3. 模型能否根据当前依据正确选择，而无需遵循穷举路线？
4. 修改后的技能能否在新会话中工作，而不依赖创建它时的对话？

不要因为模型曾经出现一次失败，就将相反行为添加为通用规则。请先判断该失败是否仍能复现、是否由提示词负责，以及同一规则是否会在另一项有效任务中造成消极等待或额外工作。

## 验证行为

文本评审只能证明一致性，不能证明有效性。请在新会话中运行有代表性的任务并比较实际结果：

- 小型变更仍保持小型；
- 普通的仓库歧义不会被交还给用户；
- 可选问题和推测性风险不会扩大范围；
- 必需的批准、契约、测试和质量检查仍然有效；
- 技能会被目标请求选择，但不会被无关请求选择；
- 删除新增指令后，会重新出现原先观察到的失败或歧义。

[rashomon](https://github.com/shinpr/rashomon) 可以在隔离环境中分别运行包含和不包含技能变更的任务。只有当输出差异能够保留原意，并且产生超出正常波动且可归因的执行收益时，才将其视为改进。

# スキル編集ガイド

スキルは、有能なモデルでも基礎知識とリポジトリだけからは安全に決められない判断を変えるために使います。境界とエビデンスには厳密でありつつ、その内側にある可逆的な経路はモデルに選ばせます。

## スキルが必要か判断する

次の条件をすべて満たすルールをスキルに残します。

- 同じ責務で繰り返し発生する判断である。
- プロジェクト、プロダクト、組織のエビデンスによって正しい選択が変わる。
- コード、設定、根拠となる成果物がすでに所有している情報ではない。
- そのルールを削除すると、判断、下流の成果、不可逆な境界、観察可能な検証のいずれかが変わる。

一般的なプログラミング知識、1つの変更に固有の設計判断、背景説明、過去のモデルの癖を防ぐためだけに追加したルールは、それだけではスキルを必要とする根拠になりません。

## 情報を正しい場所に置く

| 情報 | 置き場所 |
|---|---|
| すべてのタスクに本当に適用するルールとセッション開始処理 | `CLAUDE.md` |
| リポジトリの目的、ドメイン制約、品質基準、ディレクトリ規約、外部エビデンスの参照方法 | `/project-inject`で設定する`project-context` |
| 1つの技術的責務またはワークフローで繰り返し使う判断基準 | スキル |
| 1つの変更に関するプロダクト成果、受理済みの要件、除外事項 | PRDまたは確認済み要件の記録 |
| 信頼できる複数案から選んだ永続的な技術判断 | ADR |
| 機能固有の責務、契約、フロー、検証境界 | Design DocまたはUI Spec |
| 実装順序と実行可能なタスク境界 | 作業計画書 |
| package script、スキーマ、ルート、実行時設定 | それぞれのリポジトリ上の正本 |

既存の正本をスキルへコピーせず、その見つけ方を示します。正本だけでは表現できない解釈規則だけを追加してください。

## 予測した経路ではなく判断材料を渡す

各責務に次の4つを渡します。

| 入力 | 答える問い |
|---|---|
| 目的 | このスキルが所有する成果は何か |
| エビデンス | どの要件、リポジトリ上の事実、チェックが判断を変えるか |
| 選択基準 | エビデンスから次の行動をどう選ぶか |
| 最小限の結果 | 次の利用側が必要とする最小限の結果は何か |

「すべてのテストレーンを実行する」は作業経路を予測しています。「必要な境界を観察できる最も狭いテストを使う」なら選択基準になります。有能なモデルは、フレームワークやプロジェクト形状ごとの分岐がなくても、リポジトリのエビデンスからレーンを選べます。

### 境界制約

境界制約は、維持すべき状態を定義します。

- 確認済みの成果を実装し、記録済みの除外事項をスコープ外に保つ。
- 権限のある要件が変更しない限り、公開契約を維持する。
- 不可逆な外部操作には権限を要求する。
- 必要な振る舞いを観察できる場合にだけ完了を主張する。

これらの制約は、モデルが向上しても価値が残ります。

### 作業生成制約

作業生成制約は、現在の必要性に関係なく成果物や行動を要求します。固定された選択肢数、必須のテストレーン、すべてのリスクに対する緩和記録、固定回数のリトライ、人間が読むドキュメントの厳密なラベルなどです。

生成される作業が、現在の要件、利用側、観察可能な失敗を保護するとエビデンスが示す場合にだけ残します。それ以外は、必要な場合にその作業を選ぶ判断基準へ置き換えます。

ソフトウェアが結果をパースする場合は正確なスキーマを使います。人間が読む成果物では、下流の利用側が特定の表現を要求しない限り、意味が同じエビデンスを受け入れます。

リポジトリ内で完結する可逆的な曖昧さはモデルに解決させます。プロダクト成果、公開契約、主要な承認済み設計、ユーザーだけが持つ権限、不可逆な操作の変更が必要な場合にユーザーへ確認します。危険な操作は、可能な限り権限、サンドボックス、隔離された認証情報などの機械的な制御で境界を守ります。プロンプトの文言だけでは封じ込めになりません。

## 段階的に情報を開示する

```text
.claude/skills/api-contracts/
├── SKILL.md
├── references/        # 必要になった詳細だけを読む
└── scripts/           # スキルが所有する決定論的な処理
```

### メタデータ

`description`は目次ではなく、スキル選択のエビデンスです。責務、プロジェクト固有の価値、呼び出し側が実際に使うトリガー表現を記載します。

```yaml
---
name: api-contracts
description: このプロジェクトで共有するAPI互換性とエラーセマンティクスを適用する。HTTPエンドポイントまたは共有API型を作成・変更するときに使用。
---
```

基礎知識だけを説明するスキルには、プロジェクト固有の内容を加えるか、そのスキル自体が不要です。

### SKILL.md本文

その責務に必要なセクションだけを使います。次の順序を起点にできます。

1. 目的とスコープ
2. 根拠となる情報源と必須入力
3. 判断基準
4. 順序に依存する場合の処理ステップ
5. 実際の利用側が必要とする場合の出力形式
6. 検証と未解決入力の扱い
7. 参照資料

実行に必要な内容があるセクションだけを設けます。例外より先に通常の判断経路を置きます。依存する処理ステップには、完了を示すエビデンスと次へ進む条件を記載します。

### 参照資料とスクリプト

- 補助ファイルは`SKILL.md`から直接リンクし、参照の連鎖を避けます。
- 先に圧縮し、残った条件付きの資料を`references/`に置き、現在の判断を左右するものだけを読み込みます。
- 毎回同じ決定論的な処理を生成する場合は`scripts/`を使います。
- 必要な成果物をすでに生成できるテンプレートやスクリプトがあれば再利用します。
- 外部スキーマ、API、インフラの参照方法は`project-context`に記録します。URLだけで、すべての実行環境からアクセスできるとはみなしません。

## BP-001からBP-009で点検する

[rashomon](https://github.com/shinpr/rashomon)と同じ9つの観点を使います。

| パターン | スキルでの点検内容 |
|---|---|
| BP-001 否定形の指示 | 必要な振る舞いを先に示す。明示的な禁止は、狭い不可逆境界に限り、安全な代替手段と許可条件を併記する。 |
| BP-002 曖昧な指示 | 正しさ、スコープ、下流での利用、検証を実質的に変える曖昧さだけを明確にする。必要十分で最も制約の少ない基準を使う。 |
| BP-003 出力形式の欠落 | 実際の利用側が必要とするフィールド、順序、シリアライズだけを定義する。 |
| BP-004 構造の不足 | 優先順位、役割、依存関係が見える最小限の構造を追加する。単純なルールは文章のままでよい。 |
| BP-005 コンテキストの過不足 | 判断、行動、検証結果を変える場合にだけコンテキストを残す。プロジェクト固有の情報源を示す。 |
| BP-006 手続き制御の不足・過剰 | 真の依存関係、権限、不可逆な操作、機械が読み取る契約、完了証明にはゲートを保つ。可逆な選択には目的、根拠、選択基準を示し、経路は固定しない。 |
| BP-007 不要な例 | 原則としてルールまたは利用側が必要とする形式を使う。非自明なプロジェクト固有の対応、例外、境界にだけ最小限の例を置く。 |
| BP-008 不確実性処理の不足 | エビデンスをobserved、inferred、unknownに分ける。unknownが次の遷移を妨げる場合にだけ停止し、必要なエビデンスまたはユーザー判断を示す。 |
| BP-009 作業の無制限な生成 | 発見事項を候補として扱う。成果、境界、実際の利用側、必要な証明に必要な作業だけを残し、変更なし、再利用、根拠に基づく却下を許容する。 |

例は、説明対象の事実だけでなく、出力形式、命名、選ばれやすい解決策にも影響します。簡潔なルールで曖昧さを解消できる例は削除してください。

## スキルを作成・修正する

可能な場合はリポジトリのコマンドを使います。

```text
/create-skill このプロジェクトで使用するAPI互換性ルールを定義
/refine-skill api-contractsからファイル数のしきい値を削除し、利用側のエビデンスで判断する
/sync-skills
```

手動編集またはレビューでは、3つのゲートを順に通します。

1. **分析** — 目的と要件を保持し、スキル全体と必要な参照資料を読み、BP-001からBP-009を点検して、誤っている判断・出力を特定する。
2. **最適化** — 根拠のある各指摘を、その判断を所有するルールで解決する。成果を左右する曖昧さを除く場合、または名前を示せる要件を保護する場合にだけ制約を追加する。
3. **バランス確認** — 目的の保持、判断に十分な情報、情報密度、制約の必要性、作業量の妥当性、変更の追跡可能性を確認し、判断も有効な出力も変えない追加を削除する。

編集後は`/sync-skills`とリポジトリのスキルインデックスチェックを実行します。

## 各ルールを監査する

ルールを追加・維持する前に、次の4点を確認します。

1. そのルールを削除すると、どの判断、境界、利用側、観察可能な失敗が変わるか。
2. そのルールはスコープを制限するのか、必要性に関係なく作業を生み出すのか。
3. 網羅的な経路を与えなくても、現在のエビデンスからモデルが正しく選べるか。
4. 変更を作った会話に依存せず、新しいセッションでも修正後のスキルが機能するか。

観察した1つのモデル失敗に対して、反対の振る舞いを普遍的なルールとして追加しないでください。失敗が今も再現するか、プロンプトが所有する問題か、別の妥当なタスクで同じルールが消極性や余分な作業を生まないかを先に確認します。

## 振る舞いを検証する

文章レビューで確認できるのは整合性であり、効果ではありません。新しいセッションから代表的なタスクを実行し、実際の結果を比較します。

- 小さな変更が小さいまま完了する。
- リポジトリ内の通常の曖昧さをユーザーへ返さない。
- 任意の指摘や推測上のリスクがスコープを拡大しない。
- 必須の承認、契約、テスト、品質チェックは維持される。
- 意図した依頼でスキルが選択され、無関係な依頼では選択されない。
- 追加した指示を削除すると、観察済みの失敗または曖昧さが再発する。

[rashomon](https://github.com/shinpr/rashomon)を使うと、隔離環境でスキル変更の有無によるタスク結果を比較できます。目的を保持し、通常のばらつきを超えて追跡可能な実行上の効果がある場合にだけ改善と判断します。

# ユースケースとコマンド

プロジェクトの設定が済んでいない場合は、先に[クイックスタート](./quickstart.md)を参照してください。このページでは、開発上の目的と、それを担うコマンドを対応づけています。

## コマンドを選ぶ

### 実装・調査

| コマンド | 完了する成果 |
|---|---|
| `/implement <依頼>` | 要件を確認し、該当する設計、実装、検証、コミットまで完了する |
| `/task <依頼>` | スコープと該当スキルを確認して、単独のタスクを実行する |
| `/diagnose <問題>` | 問題を調査し、原因を独立して検証して、裏付けのある解決策を導く。解決策の実装は行わない |
| `/review [Design Doc]` | 完了したバックエンドまたは共通実装を、合意した成果、リポジトリの基準、セキュリティ上の境界に照らしてレビューし、ユーザーが承認した修正を適用する |
| `/front-review [Design Doc]` | フロントエンド実装に対して同じレビュー・修正フローを実行する |

### 設計・計画済み作業

| コマンド | 完了する成果 |
|---|---|
| `/design <依頼>` | スコープを確認し、条件を満たすADR判断を解決して、Design Docを承認まで進める |
| `/front-design <依頼>` | UIの判断が残っている場合はUI Specを追加し、フロントエンドの設計成果物を承認まで進める |
| `/plan [Design Doc]` | 作業計画書を作成・レビューして承認まで進める。必要に応じて統合/E2Eスケルトンを先に生成する |
| `/front-plan [Design Doc]` | フロントエンド作業計画書を作成して承認まで進める |
| `/build [作業計画書]` | 承認済みの計画からバックエンドまたは共通タスクファイルを実体化して実行する |
| `/front-build [作業計画書]` | 承認済みの計画からフロントエンドタスクファイルを実体化して実行する |
| `/add-integration-tests [Design Doc]` | 既存コードに、受理済みの振る舞いを証明する最小限の統合/E2Eテストを追加する |
| `/reverse-engineer <パス>` | 既存の振る舞いを調査し、レビュー済みのPRDと必要に応じたDesign Docを作成する |
| `/update-doc [ドキュメント]` | 既存のPRD、ADR、Design Docを更新・レビューし、実装には進まない |

### プロジェクト知識・スキル

| コマンド | 完了する成果 |
|---|---|
| `/project-inject` | プロジェクト固有の前提情報と品質基準を`project-context`に記録する |
| `/create-skill <知識>` | 対話的なヒアリングとレビューを通して新しいスキルを作成する |
| `/refine-skill <変更>` | 既存スキルに対象を絞った変更を適用し、結果をレビューする |
| `/sync-skills` | スキル内容の変更後にメタデータを同期する |

## よく使うフロー

### 変更を一貫して完了する

```text
/implement Webhookの署名検証を追加
```

1つの依頼をライフサイクル全体で進める場合は`/implement`を使います。最初に成果と除外事項を確認し、リポジトリのエビデンスが支持する最小限のドキュメント・実装経路を選びます。

### 単独のタスクを実行する

```text
/task 「+」を含むメールアドレスの検証不具合を修正
```

すでに成果が1つに絞られていて、設計から実装までのフローを必要としない場合は`/task`を使います。

### 修正方法を決める前に診断する

```text
/diagnose 更新後のリクエストで古いデータが返ることがある
```

`/diagnose`は、検証済みの原因と根拠のある解決策を報告します。解決策を選んだ後、別の実装指示を出してください。

### 設計・計画・実装を分ける

```text
/design Webhookの署名検証を追加
/plan docs/design/webhook-signature-design.md
/build docs/plans/20260809-feature-webhook-signature.md
```

永続的な成果物を1つずつ承認してから進める場合や、計画済みの作業を別セッションで実行する場合に個別コマンドを使います。

### 計画済みの作業を再開する

```text
/build
```

引数を省略すると、`/build`は自分が担当する消費可能なタスクセットを解決します。複数の計画が候補になる場合は作業計画書のパスを渡してください。executor laneがfrontendのタスクには`/front-build`を使います。

### 完了した実装をレビューする

```text
/review docs/design/webhook-signature-design.md
```

完了した実装が合意した成果とリポジトリの基準を満たし、不要な変更を含まず、機能、信頼性、セキュリティに関わる重大な問題がないか確認します。根拠のある指摘を提示し、ユーザーが承認した修正だけを適用して、修正後に該当箇所を再確認します。レビュー収束後に最終の品質チェックを1回実行します。レビュー修正用のタスクファイルは作成しません。

## ドキュメント経路

| 構造スケール | 条件 | 永続的な成果物 |
|---|---|---|
| 小 | まとまった成果が1つで、1つの責務境界内にリポジトリが支持する明白な実装が1つある | なし |
| 中 | まとまった成果が1つで、境界をまたぐ調整または永続的になりうる選択を含む | Design Doc → 作業計画書 |
| 大 | 独立して価値を持つ成果が複数あり、それぞれ別の設計判断を要する | PRD → Design Doc → 作業計画書 |

ファイル数は変更範囲を調べるエビデンスであり、スケールを決定するルールではありません。

- 技術的な論点は、信頼できる異なる選択肢が少なくとも2つ残り、その選択が永続的な影響を持つ場合にだけADRになります。ADRバッチはDesign Docより先に承認します。
- フロントエンドまたはフルスタックでは、画面、状態、操作、表示に関する判断が残っている場合にだけUI Specを作成します。
- 小規模では、確認済みの成果、根拠となる情報源、影響パス、観察可能な検証条件を直接実装へ渡します。形式を満たすためのドキュメントやタスクファイルは作りません。

## テスト・品質チェック

- 統合/E2Eスケルトンは、受理済みの振る舞いと証明義務から選定します。既存テストは、同じ境界を実行し、対象となる故障によって失敗する場合にだけ証明として再利用します。
- 1つのシナリオで複数の義務を証明でき、アサーションと故障の対応が明確なままであれば統合します。セットアップや故障モードが異なる場合は分けます。
- `quality-fixer`は、リポジトリ設定とタスクの検証方法からチェックを検出し、現在の変更が所有する失敗を修正します。実行できないチェックや無関係な既存失敗は記録します。
- 実行できないチェックを合格扱いにはしません。build・reviewの完了レポートに制約を引き継ぎます。

## 成果物のライフサイクル

- PRD、ADR、UI Spec、Design Docは永続的な根拠となる情報源です。
- 作業計画書は、承認済みの実装順序とタスク境界を保持します。
- 実体化されたタスクファイルは実行時のハンドオフです。buildレシピは対応する作業をコミットした後、消費したタスクファイルを削除します。

## プロジェクト固有の振る舞いを追加する

このリポジトリに固有の事実、制約、品質基準には`/project-inject`を使います。特定の責務でだけ読み込む再利用可能な判断にはスキルを使います。機能固有の判断をグローバルなルールへ複製せず、該当するPRD、ADR、UI Spec、Design Docに保持してください。

スキル内容を変更した後は次を実行します。

```text
/sync-skills
```

情報の置き場所と検証方法は[スキル編集ガイド](./skills-editing-guide.md)を参照してください。

詳細な実行契約は`.claude/commands/`配下のコマンド定義が正本です。
